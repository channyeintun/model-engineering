08

Latency and memory

A model that generates text is not one machine. It is two, and they have opposite bottlenecks. Once you can tell them apart you can predict the speed of a model before you run it, and you can measure the real speed afterwards without fooling yourself.

08 · 1Two machines wearing one model

Generating an answer has two phases, and almost every wrong intuition about speed comes from mixing them up. Take one concrete prompt and carry it through the whole lesson: 512 tokens, about a page of text. The same weights are about to do two very different jobs with it.

Prefill is the first phase. The model reads all 512 prompt tokens at once. Every one of them goes through every layer in one wide pass, in parallel. It is exactly like the batch dimension you met in Lesson 01. Here the parallel dimension is positions in the sequence, not independent examples.

Decode is the second phase. It produces one token, appends it to the sequence, and produces the next. It cannot be parallelised, because token 41 depends on token 40 having been chosen. This is a sequential loop, and it is where nearly all of the wall-clock time of a long answer goes.

The key fact is the counter on the right. During prefill the model reads every weight once and uses each one 512 times, one use per prompt position. During decode it reads every weight once and uses each one once. Same weights, completely different economics.

Remember this

Prefill is compute-bound: the chip is busy doing arithmetic. Decode is memory-bound: the chip is waiting for numbers to arrive. You must benchmark them separately, tune them separately, and on some devices you should even run them on different hardware units.

08 · 2The bandwidth wall

The word that makes this precise is arithmetic intensity: how much arithmetic you do for each byte you move from memory. It is a ratio, and it decides which resource runs out first.

The maths, once

FLOP stands for floating-point operation: one multiply, or one add. FLOPs with an s is the plural — a count. FLOP/s is the rate, a count per second. Those two get confused constantly, and everything below depends on keeping them apart.

intensity = FLOPs performed ÷ bytes moved decode, 1 token : 2N FLOPs ÷ N·b bytes = 2 / b prefill, T tokens: 2NT FLOPs ÷ N·b bytes = 2T / b N number of weights in the model b bytes per weight T prompt length, in tokens

A matrix multiply does one multiply and one add per weight, so 2 FLOPs per weight. Every weight must be read from memory once per pass, whatever the pass contains. That is the whole derivation.

Why can the chip not just keep the weights nearby and stop re-reading them? Because its own fast memory holds a few megabytes. The weights are hundreds of megabytes, often several gigabytes. There is nowhere on the chip to put them. Every pass pays for the trip from main memory again.

Put numbers in. A model quantized to Q4_K_M stores 4.89 bits per weight averaged over the whole file, so b = 0.61 bytes. (Lesson 07 works out 4.50 bits for a plain Q4_K block. The _M variant keeps a few tensors at higher precision, which lifts the file average to about 4.89.) Decode intensity is 2 / 0.61 ≈ 3.3 FLOP per byte. Prefill over our 512-token prompt is 2 × 512 / 0.61 ≈ 1 700 FLOP per byte.

Those two numbers mean nothing on their own. They mean something next to a third: the point where the chip itself is balanced. A chip is balanced when its arithmetic and its memory run out at the same moment. That happens at peak FLOP/s ÷ peak bytes/s, and you can compute it for your own device from two datasheet lines. A phone GPU doing about 4 TFLOP/s over 75.8 GB/s balances at 4e12 ÷ 75.8e9 ≈ 53 FLOP per byte. Below that number you are waiting for memory. Above it you are waiting for arithmetic. Mobile parts land between roughly 50 and 200.

Now the comparison is arithmetic rather than opinion. Prefill at 1 700 sits far above 53, so it saturates the arithmetic units. Decode at 3.3 sits far below. The share of the arithmetic units it can keep busy is 3.3 ÷ 53 ≈ 6 %. During decode, about ninety-four percent of your expensive chip is idle, waiting for bytes.

That gives the single most useful estimate in on-device work. If decode reads every weight once per token, and memory can deliver a fixed number of bytes per second, then:

tokens / second ≈ memory bandwidth (bytes/s) ÷ bytes of weights a ceiling, not a prediction — real throughput is 40 % to 70 % of it weights only for now; section 3 adds the KV cache to the bytes per token

Compute it before you write any inference code. If the ceiling is 6 tokens per second, no amount of tuning will save the product.

ceiling.pypython
BANDWIDTH_GB_S = 75.8            # your device's memory bandwidth
PARAMS         = 3_000_000_000   # 3 B weights
BITS_PER_W     = 4.89            # Q4_K_M, measured bits per weight

bytes_per_token = PARAMS * BITS_PER_W / 8
ms_per_token    = bytes_per_token / (BANDWIDTH_GB_S * 1e9) * 1000

print(f"{bytes_per_token/1e9:.2f} GB read per generated token")   # 1.83 GB
print(f"{ms_per_token:.1f} ms  ->  {1000/ms_per_token:.0f} tok/s ceiling")

Two published figures to anchor the arithmetic. An A19 Pro pairs 12 GB of LPDDR5X — a low-power memory type used in phones — running at 9600 MT/s. MT/s means megatransfers per second: how many times a second the memory hands over one bus-width of data. Bandwidth is transfer rate × bus width ÷ 8, so a 9600 MT/s memory on a 64-bit bus gives 9600e6 × 64 ÷ 8 ≈ 76.8 GB/s, and the measured figure is about 75.8 GB/s. A Snapdragon 8 Elite Gen 5 sits at about 84.8 GB/s. Do that conversion once and you can read the bandwidth off any datasheet yourself. Here is the same calculation across four model sizes at 75.8 GB/s, all at Q4_K_M:

ModelWeight bytes read per tokenms / tokenCeiling
0.5 B0.31 GB4.0~250 tok/s
1 B0.61 GB8.1~124 tok/s
3 B1.83 GB24.2~41 tok/s
8 B4.89 GB64.5~15 tok/s

This is the honest reason Part III exists. In Lesson 07 you learned that quantization makes the file smaller. The table shows that on a device it also makes the model faster, because the file size is the per-token cost. Going from BF16 to Q4_K_M shrinks the per-token read by 3.3×. torchao measures a Llama-3-8B int4 conversion running 1.89× faster — well short of 3.3×, and that shortfall is the 40 % to 70 % band again. It is a bandwidth win, not an arithmetic win.

The ceiling is not a promise

Real throughput lands at roughly 40% to 70% of this number. Part of the gap is attention over the cache; section 3 puts a number on that one. The rest is the sampling step, the tokenizer, Python, and every small operation that is not a big matrix multiply. Measure 60% of your ceiling and you are doing well. If you measure 8%, something is broken — and now you know it, because you had a number to compare against.

08 · 3The KV cache is the other half of your memory

In Lesson 04 you added a KV cache so that generating token 500 did not recompute tokens 1 to 499. That cache is what makes decode cheap in compute. It is also what makes it expensive in memory, and on a phone it is usually the thing that kills the app.

The size is exact arithmetic, not an estimate. For every token you keep in context, every layer stores one key vector and one value vector for every key/value head:

KV bytes = 2 × layers × kv_heads × head_dim × tokens × bytes_per_element 2 one key vector and one value vector layers depth of the model kv_heads key/value heads — 8 here, shared by 32 query heads head_dim head dimension, written d_h in Lesson 03 tokens how many tokens are being kept in context

Take a plausible 3-billion-parameter shape: 32 layers, 8 key/value heads, head dimension 128, cache stored in FP16. That is 2 × 32 × 8 × 128 × 2 = 131 072 bytes — about 131 kB for every single token in the context. Now watch what happens as the conversation grows.

kv_size.pypython
def kv_bytes(layers, kv_heads, head_dim, tokens, bytes_per_element=2, batch=1):
    """Keys and values, for every layer, for every token kept in context."""
    return 2 * layers * kv_heads * head_dim * tokens * bytes_per_element * batch

WEIGHTS_MB = 1830        # the same 3 B model at Q4_K_M

print(f"{kv_bytes(32, 8, 128, 1)/1e3:.1f} kB per token")      # 131.1 kB per token

for ctx in (512, 2048, 8192, 32768):
    mb = kv_bytes(32, 8, 128, ctx) / 1e6
    print(f"{ctx:6d} tokens -> {mb:8.1f} MB  ({mb/WEIGHTS_MB:5.0%} of the weights)")

At 512 tokens the cache is 67 MB and nobody notices. At 8 192 tokens it is 1.07 GB, about six tenths of the weights. At 32 768 tokens it is 4.29 GB — more than twice the weights, and far past what a phone will let one app hold.

Now go back and repair the ceiling from section 2. Attention re-reads the whole cache on every decode step. So the bytes the chip must move to produce one token are not just the weights:

bytes per token = weight bytes + cache bytes at 512 tokens: 1.83 + 0.07 = 1.90 GB -> 75.8 / 1.90 ≈ 40 tok/s at 8 192 tokens: 1.83 + 1.07 = 2.90 GB -> 75.8 / 2.90 ≈ 26 tok/s

Read that as a promise about how the app will feel. Generation gets slower as the conversation gets longer, and now you can say by how much. Predict with the weights alone for a short prompt. Add the cache whenever you quote a number at your maximum context, which is the only number worth quoting.

Two more consequences follow immediately. First, grouped-query attention (GQA) from Lesson 03 is not a quality trick, it is a memory trick: with 32 query heads and no sharing, this cache would be four times larger. Second, quantizing the weights to 4 bits and leaving the cache at FP16 solves half of your problem at long context. The cache is a separate decision, with its own precision setting.

The limit that arrives late

A memory bug caused by the KV cache does not appear at launch. It appears after a long conversation, on the user's device, with your app in the background. Always test at your maximum advertised context length, and set a hard cap you enforce in code.

08 · 4Batch size, and why the server trick does not travel

On a server, the standard answer to "decode is memory-bound" is batching. Collect several users' requests and run one decode step for all of them together. Every weight you read is now used B times instead of once, so intensity becomes 2B / b. At B = 32 a memory-bound workload turns into a compute-bound one, and the machine serves several times more people at no cost to any one of them.

On a device there is one user. B is 1 and cannot be anything else. There is no second request to share the weight read with. So the whole family of server techniques built on batching is solving a problem you do not have. Continuous batching slots a new request into the running batch as soon as another one finishes. Paged attention stores each user's KV cache in fixed-size blocks, so memory does not fragment when users come and go. Both are about fitting many people onto one machine. You have one person.

Server, many users

  • Batch size 16 to 256. Weights read once, used many times.
  • Decode becomes compute-bound. The GPU is the scarce resource.
  • KV cache memory grows with batch size — that is what limits how many users fit.
  • The metric that matters is tokens per second per dollar.

Device, one user

  • Batch size is always 1. Every weight read serves one token.
  • Decode is memory-bound, permanently. Bandwidth is the scarce resource.
  • KV cache memory grows with context length only.
  • The metrics that matter are time to first token and sustained tokens per second.

There is one batch you do still have, and you already met it: prefill. Processing 512 prompt positions at once is a batch over positions. It is exactly why prefill saturates the compute units while decode does not. It is also why the fix for a slow first response differs from the fix for slow generation.

There is one honest way to get a batch out of a single user, and you should know its name. In speculative decoding a small, fast draft model guesses the next few tokens. The big model then checks all of those guesses in one pass — a batch over positions, exactly like prefill. Verify 4 drafted tokens in a single read of the weights and the intensity rises from 2 / b to 8 / b. When the draft agrees often you get roughly 1.5 to 2 times the decode rate. When it does not you get nothing, and it costs a second model in memory either way. We do not use it again here. Keep it as the exception: bandwidth ÷ weights is a law about producing one token at a time, not about generation itself.

08 · 5What torch.compile actually buys

A single decode step launches a few thousand tiny programs on the chip. Each one costs a launch and a round trip to memory that has nothing to do with your model. On a server, with a batch of 64 sharing every launch, that overhead vanishes into the noise. On a phone, one token at a time, it is a real slice of your budget. This section gets that slice back.

First the two words. A kernel here is one small program the chip runs: one for the matrix multiply, one for the normalisation, one for the activation function. This is not the convolution kernel of Lesson 02 — same word, different thing. Eager mode is how PyTorch has behaved in every lesson so far: it launches each kernel the moment Python reaches that line, one operation at a time.

Each kernel reads its input from memory, does its work, and writes its output back. For a big matrix multiply that round trip is irrelevant — the arithmetic dominates. For the small operations around it the round trip is the cost. Put numbers on one. An RMSNorm over a single activation of 3 072 values in FP16 reads 6 kB and writes 6 kB. It does roughly 3 operations per value, so about 9 000 operations against 12 kB of traffic. That is an intensity below 1 FLOP per byte, on a chip balanced at 53. The arithmetic is free; the traffic is everything.

Kernel fusion writes one kernel that performs the whole chain while the values are still in registers. The middle tensors are never written to memory and never read back. That is the main thing torch.compile does for you, and it also removes the per-operation Python overhead.

So the arithmetic of the section is this. A normalisation, a scale and an activation, run eagerly, cost six trips to memory and 36 kB of traffic. Fused into one kernel they cost two trips and 12 kB, and the two intermediate tensors are never born. On a laptop GPU the usual result of compiling a decode loop is 10 % to 30 % off the latency. If your model is dominated by one big matrix multiply it can be close to zero. Measure it; do not assume it.

What it cannot do

Fusion cannot make the weight read smaller. If you are bandwidth-limited on the weights themselves — which is exactly what decode is — compilation gives you back the elementwise traffic and the launch overhead, not the matrix-multiply traffic. The lever for that is fewer bits per weight, which is Lesson 07. Compilation and quantization attack different lines of the same budget.

Two practical warnings. First, torch.compile compiles on the first call, and that can take far longer than the inference you are trying to measure. It belongs inside your warm-up, never inside the timed region. Second, decode changes the sequence length on every step. If the compiled graph is specialised on a shape, a changing shape forces a recompile, and you can spend more time compiling than generating. Check the recompile count before you conclude that compilation did not help.

08 · 6Measuring without lying to yourself

Here is the single most common mistake in this whole subject. It reports 0.4 ms for a step that really took 24.2 ms — wrong by a factor of sixty, and still completely reasonable-looking on the screen.

When you call a model on a GPU — CUDA or Apple's MPS — Python does not wait for the result. It puts the work on a queue and returns immediately. If your clock starts before the call and stops after it, you have measured how fast Python can fill a queue. You have not measured the model at all.

The fix is a synchronisation call, which blocks until the device queue is empty. Put one before you start the clock and one before you stop it. And throw away the first few runs: the first pass allocates buffers, compiles kernels, and fills caches, so it can be many times slower than the steady state.

time_it.pypython
import time, torch
torch.set_grad_enabled(False)

def sync():
    if torch.cuda.is_available():            torch.cuda.synchronize()
    elif torch.backends.mps.is_available():  torch.mps.synchronize()

t0 = time.perf_counter()                     # WRONG: times the queue, not the model
model(x)
wrong = time.perf_counter() - t0

for _ in range(5):                           # warm up: allocator, kernels, caches
    model(x)
sync()

times = []
for _ in range(20):                          # RIGHT: sync on both sides, repeat
    sync()
    t0 = time.perf_counter()
    model(x)
    sync()
    times.append(time.perf_counter() - t0)

times.sort()
print(f"wrong  {wrong*1e3:7.2f} ms")
print(f"median {times[len(times)//2]*1e3:7.2f} ms")

Take the median, not the mean. One background app waking up will pull a mean a long way; the median ignores it. To report spread, give the median and the 90th percentile — a user feels the slow requests, not the average one.

Next, split the measurement in two. A single "tokens per second" number hides the thing users complain about. Time to first token is prefill plus one decode step, and it is what the interface feels like. Decode rate is everything after that.

ttft_and_rate.pypython
NEW  = 128                                   # tokens generated after the first
WARM, REPS = 3, 5

def median_time(fn):
    for _ in range(WARM):                    # same recipe as time_it.py
        fn()
    ts = []
    for _ in range(REPS):
        sync()
        t0 = time.perf_counter()
        fn()
        sync()
        ts.append(time.perf_counter() - t0)
    return sorted(ts)[len(ts) // 2]          # median, never the mean

def gen(n):
    model.generate(**inputs, max_new_tokens=n, do_sample=False)

ttft  = median_time(lambda: gen(1))          # prefill + one decode step
total = median_time(lambda: gen(NEW + 1))
# assumes prefill costs the same in both calls — true only after warm-up

print(f"prompt tokens        {inputs['input_ids'].shape[1]:7d}")
print(f"time to first token  {ttft*1e3:7.1f} ms")
print(f"decode rate          {NEW/(total-ttft):7.1f} tok/s")

Use greedy decoding (do_sample=False) while benchmarking. Sampling adds randomness to the output length and to the work done. The only thing that changes between two runs should be the thing you changed.

For memory, ask the device rather than the operating system. On CUDA, torch.cuda.reset_peak_memory_stats() and torch.cuda.max_memory_allocated() give a true peak across the run. On Apple Silicon, torch.mps.current_allocated_memory() reports the current allocation, so sample it at the end of generation, when the cache is largest. Report peak memory at your longest supported context, never at your demo prompt.

Finally, when a number is bad and you do not know why, open the profiler instead of guessing. It tells you which operators consumed the time, which is usually a surprise.

profile_it.pypython
from torch.profiler import profile, ProfilerActivity

acts = [ProfilerActivity.CPU]
if torch.cuda.is_available():
    acts.append(ProfilerActivity.CUDA)

for _ in range(3):                           # warm up before profiling, always
    model.generate(**inputs, max_new_tokens=8, do_sample=False)

with profile(activities=acts, record_shapes=True) as prof:
    model.generate(**inputs, max_new_tokens=16, do_sample=False)

print(prof.key_averages().table(sort_by="self_cpu_time_total", row_limit=12))
The recipe, in six lines

Fix the prompt and use greedy decoding. Warm up and discard. Synchronise before and after the timed region. Repeat and take the median. Report time to first token, decode rate and peak memory as three separate numbers. Compare the decode rate with the bandwidth ceiling you computed in section 2.

08 · 7Heat, eviction, cold start, and the app store

Everything above is true on a laptop with mains power. A phone adds four constraints no laptop benchmark will show you.

Cold start. The first run of your app is not the run you measured. It has three parts, and they have wildly different sizes. Opening the file and mapping it into memory is nearly free. Then the runtime turns the model into code for this particular device and caches the result. On Apple that artifact is a .mlmodelc built by Core ML; in a browser it is compiled WebGPU shaders. You meet both properly in Lesson 10. This step is usually the largest single cost. Prefill of the first prompt comes last. Measure all three separately: only one of them has an easy fix.

The numbers from the animation, written out so you can check the addition:

Compile the model for the backend2 400 ms40 ms

One row moved and the wait fell by a factor of six. So the fix for a slow cold start is caching the compiled artifact, not buying faster storage. And measure cold start cold: the second launch reads a warm page cache and tells you a comfortable lie.

Thermal throttling. A phone has no fan. Under sustained load it heats up, and the system lowers the clock speed to protect the battery and your hand. This begins after roughly 30 to 120 seconds. The run below opens at 25 tokens per second. That is about 60 % of the 41 tok/s ceiling from section 2, so it is a healthy measurement, not a record. It steps down to 17 after about 45 seconds, and settles at 13 after two minutes. Averaged over three minutes that is about 18 tokens per second. A ten-second benchmark would have published 25 — a state your users are almost never in.

Memory eviction. iOS shuts down apps that go over a memory budget. On a 6 GB phone a foreground app may only safely hold about 2 to 3 GB. Reading the weights straight from the file helps. The system already has a copy of them on disk. If memory runs short it can throw them out and read them back later. The KV cache is memory you allocated and wrote into yourself. It has no copy on disk, so it cannot be thrown out. That is why the cache is the dangerous half.

Download size. Apple restricts App Store downloads over cellular above 200 MB, and Google Play caps the base module of an Android App Bundle at about the same. Your weights will not fit, so do not ship them inside the binary. Download them on first run, check a hash, and keep them in a cache directory the system is allowed to empty. Lesson 10 works through the real budgets and the shipping side.

The benchmark that fooled everybody

A ten-second run, on a plugged-in laptop, with a warm page cache, a 20-token prompt, and no synchronisation. Every one of those five choices makes the number better than reality. Change all five and you often find the honest figure is a small fraction of the one in the announcement.

Check yourself

Your model is 1.0 GB of weights and your device delivers 50 GB/s of memory bandwidth. What is the ceiling for single-user decode?

Decode reads every weight exactly once per token, so the rate is bandwidth divided by model bytes: 50 ÷ 1.0 = 50. The FLOP count does not enter, because the arithmetic units are idle while they wait for the bytes.

On an Apple Silicon Mac you time a decode step with time.perf_counter() and get 0.4 ms, which would be 2 500 tokens per second for a 1 B model. What has gone wrong?

GPU calls are asynchronous: Python returns as soon as the work is submitted. Without torch.mps.synchronize() on both sides of the timed region you are timing the queue. The bandwidth ceiling is the giveaway — 2 500 tok/s on a 1 B model is physically impossible.

Time to first token on a 4 000-token prompt is 1.9 seconds, but generation afterwards feels fine. Which change helps that first number most?

Time to first token is dominated by prefill, which is compute-bound and grows with prompt length. Halving the bytes per weight speeds up decode, which was already fine. Batch size is fixed at 1 on a device, and cache precision affects memory, not prefill compute.

A model has 28 layers, 4 key/value heads and a head dimension of 128, and keeps its KV cache in FP16. At roughly what context length does the cache pass 1 GB?

Per token the cache costs 2 × 28 × 4 × 128 × 2 = 57 344 bytes, so 1 GB buys 1e9 ÷ 57 344 ≈ 17 400 tokens. Halve the key/value heads to 2 and the per-token cost halves too, so the same 1 GB now stretches to about 34 800 tokens. That doubling is the whole reason grouped-query attention exists.

Key words from this lesson
Prefill also: prompt processing
The first pass, where the whole prompt goes through the model at once. Compute-bound.
Decode also: generation
The loop that produces one token at a time after the prompt. Memory-bound.
FLOP floating-point operation
One multiply, or one add. FLOPs is a count of them. FLOP/s is a rate, a count per second.
Arithmetic intensity
How many arithmetic operations you perform for each byte you read from memory. A ratio that tells you which resource runs out first.
Balance point of a chip
Peak FLOP/s divided by peak bytes per second. Work below it waits for memory; work above it waits for arithmetic.
Kernel in the GPU sense
One small program the chip runs, such as a matrix multiply or a normalisation. Not the convolution kernel of Lesson 02.
Kernel fusion
Writing one kernel that does a chain of small operations while the values stay in registers, so the middle results never reach memory.
Memory bandwidth measured in GB/s
How many bytes per second the memory can deliver to the chip. The hard limit on generation speed.
Time to first token often written TTFT
How long the user waits before anything appears. Prefill plus one decode step.
Warm-up
Runs at the start of a benchmark that you throw away, because the first pass also pays for allocation and compilation.
Synchronisation /ˌsɪŋkrənaɪˈzeɪʃn/
Waiting until the device has finished the work you submitted. Without it, a clock measures the queue.
Thermal throttling
The system lowering clock speeds because the chip is too hot. It turns a fast short benchmark into a slower long one.
Cold start
The first run after launch: mapping the file, compiling for the backend, and prefilling the first prompt.
