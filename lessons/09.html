09

Export: leaving PyTorch

A trained model is a Python object. A phone is not a Python interpreter. This lesson is about the file you hand over at the border. How it is made, which four borders you can cross, and how to prove the model still works on the other side.

Part IV · Ship it ≈ 130 min reading Project · The same model, four formats Needs · Lessons 04, 05, 07, 08

By the end you can

  • Say what torch.export produces, and how it differs from the older tracing and scripting.
  • Choose between ExecuTorch, the Open Neural Network Exchange (ONNX), Core ML and the GPT-Generated Unified Format (GGUF) for a given target, and name the cost of each.
  • Declare dynamic shapes so an export does not break on the second input you give it.
  • Read a partition report and say which part of your graph really runs on the accelerator.
  • Verify an export numerically against PyTorch, with a tolerance you can defend.

09 · 1Why you cannot ship Python

Everything you have built so far lives inside a Python process. A nn.Module is a Python class. Its forward method is Python code that calls into the PyTorch C++ library, one operator at a time, deciding what to do next while it runs.

That mode — one operator, then a decision, then the next operator — is called eager execution. Eager means the Python is still in charge. The word turns up in export error messages and throughout this lesson, so attach it now. The design is excellent for research. It is unusable as a product for three separate reasons.

Size. To run your model, a device would need a Python interpreter plus the full PyTorch library. That is hundreds of megabytes before your weights. App stores limit what you may download; browsers have no Python at all.

Speed. Every operator costs a trip through the Python interpreter. On a server with large batches that overhead disappears into the arithmetic. On a phone generating one token at a time it does not.

Platform. An iOS app cannot ship a general Python runtime. A web page cannot import torch. An embedded board has no filesystem to install packages into. These are not performance problems; they are hard walls.

So you stop shipping a program and start shipping data: a frozen description of the computation, plus the numbers, in one file. A small C++ runtime — a few megabytes, not a few hundred — reads that file and executes it. The word for making that file is export.

Remember this

Export is not one action. It is three, and they fail in different ways. Capture turns Python into a graph. Lowering rewrites the graph's operators into what a backend understands. Partitioning decides which piece of the graph each accelerator gets. When people say "the export failed", ask which of the three.

Two models travel with you through this lesson, and they have different jobs. The tiny GPT you trained in Lesson 04 is the warm-up. It is small, it is yours, and you understand every line of it, so when an export fails you can go and look. The model you fine-tuned in Lesson 05 is the one you ship. That is the file Lesson 10 runs on a device and Lesson 13 loads as the assistant's brain.

For the model you ship, three steps happen in a fixed order, and it is the order of this course. First, merge your LoRA — low-rank adaptation — adapter into the base weights (Lesson 05). A graph of frozen weights plus a side branch is harder for every backend than one plain weight matrix. Second, quantize (Lesson 07), because the target toolchain expects to see the low-precision weights it will store. Export last.

Exporting an FP32 model and hoping the runtime will shrink it later is how people end up with a 1.4 GB artefact they cannot ship. That is the same 1440 MB you measured in Lesson 07, and the same model, at INT4, was 191 MB.

09 · 2What torch.export actually produces

torch.export.export() runs your model once, with example inputs you provide, and writes down every tensor operation it sees. It does not write down the Python around those operations. That single sentence explains nearly every export problem in this lesson.

The result is an ExportedProgram. It holds four things:

  • A single, flat graph of ATen operators — PyTorch's small, fixed vocabulary of primitive tensor operations. No Python, no classes, no method calls.
  • The weights, kept in a separate state dictionary rather than baked into the graph.
  • A graph signature that says which graph inputs are parameters, which are buffers, and which are the arguments a caller passes.
  • Shape constraints: which dimensions are fixed numbers, which are symbols, and what range each symbol may take.
export_graph.pypython
import torch
from torch.export import export, Dim

model = TinyGPT().eval()                 # your model from Lesson 04
ids = torch.randint(0, 4096, (1, 128))   # one example input

ep = export(model, (ids,), dynamic_shapes={"ids": {1: Dim.DYNAMIC}})

print(ep.graph_module)        # the flat ATen graph
print(ep.graph_signature)     # parameters vs buffers vs user inputs
print(ep.range_constraints)   # e.g. s0 in [1, inf)

torch.export.save(ep, "gpt.pt2")

Ignore dynamic_shapes and s0 for one more section. §4 is entirely about them. For now, s0 is simply the name export gave to a dimension it agreed to leave open, and [1, inf) is the range it will accept.

The keys in dynamic_shapes are the argument names of your forward method. If forward(self, ids) becomes forward(self, tokens), the key must change too.

You will meet two older tools in old code. torch.jit.trace also ran the model once, but it folded the weights into the graph and recorded nothing about which shapes could change. torch.jit.script parsed a subset of Python, so it could keep an if statement, but the subset was small and its errors were hard to act on. torch.export replaces both.

Common trap

In current PyTorch (2.13.0), export takes strict=False by default. Non-strict capture traces through the normal Python runtime. Passing strict=True captures through TorchDynamo instead. TorchDynamo is PyTorch's bytecode-level tracer: rather than running your Python and watching the tensors go by, it reads the Python itself and refuses anything it cannot prove. It is stricter, and it rejects assumptions that non-strict capture accepts in silence. This is the reverse of the original default, so any tutorial written before this change tells you the wrong thing. When an export succeeds but the graph looks too simple, re-run it with strict=True and read the complaints.

The saved .pt2 archive is a portable intermediate, not a device format. No phone runtime loads it. It is the hand-off point: the artefact you keep in version control and feed to each of the four converters below.

09 · 3The four destinations

An ExportedProgram is still not a file a phone can run. Four tools can turn it into one, and each answers the same two questions differently: which runtime will read this file, and who maintains that runtime? Three of the four start from the ExportedProgram you just made. The fourth ignores capture and reads your checkpoint instead. Read this section for what each one costs; §8 turns the same four into a table you can decide from.

ExecuTorch — staying inside PyTorch

ExecuTorch is PyTorch's own on-device runtime. It reached 1.0 on 17 October 2025, and the release you install today is 1.4.1. Its wheel — the pre-built package pip downloads — supports Python 3.10 to 3.14.

The artefact is a .pte file. It is a flatbuffer: a binary layout you read straight from disk, with no parsing step first. Inside are the lowered program, any compiled backend blobs, and normally the weights. The layout is what lets the runtime mmap the file — map it into memory and read pages on demand, instead of loading all of it up front.

to_pte.pypython
from executorch.exir import to_edge_transform_and_lower
from executorch.backends.xnnpack.partition.xnnpack_partitioner import XnnpackPartitioner

et = to_edge_transform_and_lower(
    ep,                                    # the ExportedProgram from above
    partitioner=[XnnpackPartitioner()],    # CPU backend, works everywhere
).to_executorch()

with open("gpt.pte", "wb") as f:
    f.write(et.buffer)

The list you pass to partitioner= is the whole story of ExecuTorch. Three words get confused constantly, and the rest of this lesson depends on keeping them apart:

  • A backend is the hardware target, plus the code that runs on it — CPU kernels, GPU shaders, an accelerator compiler.
  • A partitioner is the Python object you pass at export time. It walks the graph on one backend's behalf and claims the nodes that backend can run.
  • A delegate call is the single graph node that replaces each claimed run of operators. One call in, one call out, the backend's business in between.

Whatever no partitioner claims stays as a portable CPU kernel. That is why a single .pte can target very different hardware. Several rows below name an NPU — a neural processing unit, a fixed-function accelerator built only for neural-network arithmetic. It sits beside the CPU and the GPU on most recent phone chips. Apple's version is called the Neural Engine.

Meta runs ExecuTorch in production inside Instagram, WhatsApp and the Ray-Ban Display glasses, so the runtime itself is not the risky part.

ONNX — the widest reach

ONNX — Open Neural Network Exchange — is a format defined by a committee rather than by one framework, which is both its strength and its cost. The graph is written in an opset: a numbered version of the operator vocabulary. onnx 1.22.0 introduces opset 27. You pick the opset your runtime supports — a newer opset has more operators and fewer awkward rewrites, an older opset runs in more places.

to_onnx.pypython
import numpy as np, onnxruntime as ort
import torch
from torch.export import Dim

torch.onnx.export(model, (ids,), "gpt.onnx", dynamo=True,
                  dynamic_shapes={"ids": {1: Dim.DYNAMIC}})

sess = ort.InferenceSession("gpt.onnx", providers=["CPUExecutionProvider"])
out = sess.run(None, {"ids": np.random.randint(0, 4096, (1, 200)).astype("int64")})
print(out[0].shape)

dynamo=True is the current path. It goes through the same torch.export capture described above, driven by the same TorchDynamo tracer, in place of the older direct tracer. That is why the ONNX path and the ExecuTorch path now fail in the same ways. ONNX Runtime's word for a backend is an execution provider. You pass a priority list: CoreMLExecutionProvider, QNNExecutionProvider for Qualcomm's Hexagon NPU, XNNPACK, OpenVINO for Intel CPUs and their integrated accelerators, WebGPU, CPUExecutionProvider. The runtime then partitions your graph across them, exactly like ExecuTorch's partitioners.

Two ONNX facts matter for devices. For phones there is ORT Mobile — ORT is the usual short form of ONNX Runtime. You convert .onnx to .ort, which bakes the runtime optimisations into the file, then compile ONNX Runtime with only the operator kernels your models actually use. That "reduced operator kernel build" is what takes the binary from tens of megabytes to a few. For browsers there is onnxruntime-web, at 1.27.0 on npm — the JavaScript package registry — which runs your graph on WebGPU or on WebAssembly. You will use it in Lesson 10.

Core ML — the Apple path

Core ML is Apple's own format and runtime, and the only supported way to reach the Neural Engine. You convert with coremltools, currently 9.0, and get an .mlpackage.

to_coreml.pypython
import coremltools as ct

mlmodel = ct.convert(
    ep,                                              # or a torch.jit.trace result
    minimum_deployment_target=ct.target.iOS26,
    compute_units=ct.ComputeUnit.CPU_AND_NE,         # ask for the Neural Engine
)
mlmodel.save("Gpt.mlpackage")

Two constraints of the Neural Engine decide what your conversion produces, and they explain most disappointing Core ML benchmarks:

  • It is built for FP16. Any operator that forces FP32 falls back to the GPU or the CPU.
  • It prefers four-dimensional tensors laid out as (B, C, 1, S) — batch, channels, a dummy dimension of 1, and sequence length. Unusual ranks and permutes push work off the Neural Engine, with no error and no warning.

Two more constraints are about run time rather than conversion. You never ask for the Neural Engine: you request CPU_AND_NE and Core ML decides per operator. And the .mlpackage is compiled on the device into .mlmodelc the first time it loads, which becomes your cold start. Lesson 10 measures both on a real device.

Worth knowing

coremltools 9.0 documents support for PyTorch 2.7, while this course pins torch 2.13.0. With 2.13 installed you should expect converter warnings, and sometimes a hard failure. Keep a second virtual environment with torch 2.7 only for the Core ML step. This is normal: converters always trail the framework they read.

GGUF — a separate world

GGUF — GPT-Generated Unified Format — is the file format used by llama.cpp. It is the one destination on this page that is not a torch.export backend. There is no partitioner, no opset, no lowering pass. llama.cpp ships a Python conversion script that reads a Hugging Face checkpoint. That checkpoint is a safetensors file — a plain container that stores raw tensors and nothing executable — plus the config plus the tokenizer. The script writes a GGUF file directly. A second tool then rewrites the tensors into a quantized form such as Q4_K_M.

Two numbers get quoted for that format, and they are not in conflict. Lesson 07 derived 4.50 bits per weight by hand, for one plain Q4_K block. The _M variant keeps some tensors wider than that. Across a whole file the measured average comes out near 4.89 bits per weight, which is the figure Lesson 08 built its bandwidth table on.

What you get in return is a single self-contained file. The GGUF header is a typed key-value block: general.architecture, llama.context_length, tokenizer.ggml.tokens, the chat template, the RoPE (rotary position embedding) settings. The tokenizer lives inside the weights file. There is no tokenizer.json to lose and no Python at run time. The tensor data is padded to an alignment boundary, so the whole file can be mmap-ed straight from the page cache.

The price is architectural. llama.cpp must already implement your architecture in C++. The transformer you invented in Lesson 04 will not convert, however small it is. The model you fine-tuned in Lesson 05 will, because it is a standard Llama-shaped model that llama.cpp already knows. GGUF is the right answer when you want to run a known architecture on a laptop, a desktop CLI or a server. It is the wrong answer when you need your own graph on a phone NPU.

09 · 4Dynamic shapes: the first thing that breaks

Drop the dynamic_shapes argument from §2's script for a moment, and watch what happens. Capture runs your model once, with your example input. Every shape it observes becomes a constant in the graph. This is the single most common beginner export bug, and it is invisible until the second call.

You control this with the dynamic_shapes argument. It mirrors the structure of your inputs: for each argument, a dictionary from dimension index to a specification.

SpecificationMeaningUse it when
NoneStatic. The number from your example is baked in.The dimension genuinely never changes — channels, hidden width.
Dim.DYNAMICDynamic, range inferred by export. If export finds it must pin this dimension down, it raises an error and names the guard that forced it.The normal choice for batch and sequence length.
Dim.AUTODynamic if export can manage it. In the same situation it silently makes the dimension static instead, so the export succeeds with the bug still inside.You are exploring an unfamiliar model and want no errors yet.
Dim("T", min=1, max=512)A named symbol with an explicit range.A backend needs an upper bound to plan memory ahead of time.

Every dynamic dimension becomes a symbol: s0, s1, and so on. Every comparison your model makes against that dimension becomes a guard. A guard is a condition recorded at capture time and checked on every call.

Guards are why an export can accept 200 tokens and reject 201. Here is the whole mechanism in one line. Suppose your attention block splits the sequence into blocks of 8:

where a guard comes frompython
x = x.view(B, T // 8, 8, d)      # B batch, T sequence length, d model width

# export records the guard:  T % 8 == 0
#   T = 200  ->  200 % 8 == 0   ->  runs
#   T = 201  ->  201 % 8 == 1   ->  refused

Nothing is wrong with the model. The reshape needs the length to divide evenly, so export wrote that requirement down. Attention implementations that block or tile the sequence are the usual source of these guards, and so is anything that pads to a multiple.

Whichever guard fires — the modulo above, or the plain equality you get from exporting with no dynamic_shapes at all — the error names the offending dimension by position. It looks like this, and the number in it is the number you exported with:

a real shape-guard failuretext
RuntimeError: Expected input at *args[0].shape[1] to be equal to 128,
but got 200.  If you meant this dimension to be dynamic, pass
dynamic_shapes={"ids": {1: Dim.DYNAMIC}} to torch.export.export().

Read it as three facts. *args[0] is the first argument. .shape[1] is its second dimension. equal to 128 is the guard, and 128 came from the example input you captured with.

Common trap

Marking everything dynamic is not the safe option. Each symbol is knowledge the compiler no longer has, so it cannot fold constants, cannot pick a specialised kernel, and on some backends cannot plan memory at all. Mark the dimensions that really vary — batch and sequence length — and leave the rest as None.

09 · 5What cannot be captured, and partial delegation

Capture records tensor operations. Anything that asks Python a question about a tensor's values forces the answer to be decided once, at capture time, and then frozen. The list is short and worth memorising:

  • if x.sum() > 0: — a branch on data. One side is captured; the other disappears.
  • while not done: — a loop whose length depends on data. It is unrolled to whatever length it happened to run.
  • .item(), .tolist(), int(x), a NumPy call — each pulls a tensor value into Python and turns it into a constant.
  • print() and Python assert statements on tensor values — they vanish, so a "safety check" in your forward pass is not in the shipped model.

For real data-dependent control flow there are graph-level replacements: torch.cond for a branch and torch.while_loop for a loop. Both take the branches as functions and become real nodes in the graph, so the decision happens on the device. ExecuTorch has executed them at run time since version 1.1.0. They cost you: both branches must have the same output shapes and dtypes, and both are compiled into the artefact.

The second obstacle is operators the backend does not implement. Here the toolchains are generous, and that generosity hides a cost. The unit of that generosity is the island: a maximal run of neighbouring operators that one backend agreed to take. The whole run is then replaced by a single opaque delegate call into that backend.

A model that "runs on the NPU" is usually three to ten islands with CPU glue between them. Each island boundary moves a tensor between memory the accelerator can address and memory the CPU can address. For a small tensor that copy is nothing.

For an activation of several megabytes it is not nothing. That copy happens at every boundary, on every token, and it can cancel the whole speed-up. This is the memory-bound arithmetic from Lesson 08 again: the time goes into moving bytes, not into doing maths. Only now the bytes are activations crossing a border, rather than weights being read.

When an operator is refused, the toolchain usually says so in a line you can act on. Two forms are common, and both name the operator:

what a refusal looks liketext
[XnnpackPartitioner] node aten.topk.default not supported, left on CPU
[coremltools] Op "aten::sort" not implemented for target iOS26

Reading the partition report

Everything above is invisible unless you go and look. So look. ExecuTorch will tell you, in one function call, exactly which nodes the backend took:

partition_report.pypython
from executorch.devtools.backend_debug import get_delegation_info

info = get_delegation_info(et.exported_program().graph_module)
print(info.get_summary())
print(info.get_operator_delegation_dataframe())
outputtext

num_delegated_nodes     : 7

Read three numbers, in this order. The delegated fraction: 7 of 9 nodes, so 78% of the graph reached the backend. The subgraph count: 2, which is two islands, which is four boundary crossings on every call. The leftovers: sort and topk, where you would start if you wanted 78% to be higher.

A good report has a high fraction and few subgraphs. 90% delegated across eleven islands pays twenty-two copies per token, and is often slower than plain CPU. Fraction alone is not the answer.

Common trap

Passing a partitioner is not evidence that the delegate ran. The export succeeds either way, because unclaimed nodes fall back to CPU kernels. Two exports of the same model can both "succeed" while one runs 95% of the graph in two islands and the other runs 40% of it in nine. Print the report and read the numbers.

09 · 6State: the KV cache crosses the border

A vision model is a pure function: pixels in, scores out. A language model in generation mode is not. It carries a key-value (KV) cache from one call to the next, so that producing token 501 does not recompute tokens 1 to 500. You met that cache in Lesson 04. It is the single hardest part of exporting a language model, because a graph, by construction, has no memory.

There are two designs, and the difference is arithmetic, not taste. The symbols are the course's usual ones, from Lesson 03:

  • n_layers — the number of layers.
  • G — the number of key-value heads per layer.
  • d_h — the head dimension, the width of one head.
  • T — the number of cached positions so far.
  • b — bytes per element. FP16 gives b = 2.
The maths, once
cache in and out : 2 · n_layers · G · T · d_h · b bytes moved per token cache as state : 2 · n_layers · G · d_h · b bytes moved per token

The 2 is keys and values. It is the same line Lesson 03 asked you to memorise, minus the T in the second row. And T grows with every token you generate.

Put the Lesson 04 model in and the difference stops being abstract. That model has 8 layers, 6 key-value heads, head dimension 64, at FP16, so b = 2:

DesignArithmeticBytes moved per token
Cache as state2 × 8 × 6 × 64 × 212,288 B = 12 KiB
Cache in and out, at T = 20012,288 × 2002,457,600 B = 2.34 MiB
Cache in and out, at T = 100012,288 × 100012,288,000 B = 11.7 MiB

Twelve kibibytes against nearly twelve mebibytes, for the same token. And the state row never grows: 12 KiB at position 10, 12 KiB at position 4000. That is what the missing T buys you.

The first design keeps the graph pure. The cache is an extra input and an extra output, and the caller passes the new one back in. Every runtime supports it, and ONNX language models conventionally do exactly this. The second gives the model a mutable buffer it owns. coremltools 9.0 added ct.StateType for it. You declare one state tensor of shape (2, n_layers, B, G, T_max, d_h), where B is the batch and the leading 2 is again keys and values. Then you write one slice per step. ExecuTorch calls the same idea a mutable buffer.

Whichever you choose, the position dimension is dynamic and it has a maximum. That maximum is your context limit, and you choose it at export time rather than at run time. Pick it deliberately, because the cache is allocated for the maximum on the first call, not for the length you happen to use.

Count that allocation, and be careful which context you count. First the weights, so there is something to compare against: 15,735,168 parameters at 2 bytes each is 31,470,336 bytes, or 30 MiB. That is Lesson 04's 31 MB, in the binary units this section uses throughout.

Lesson 04 trained this model with a 256-token block. At that limit the cache is 2 × 8 × 6 × 64 × 256 × 2 = 3,145,728 bytes, or 3 MiB. That is a tenth of the weights, exactly as Lesson 04 says. Now export the same model with a 4096-token context, which is what a chat prompt asks for. 2 × 8 × 6 × 64 × 4096 × 2 is 50,331,648 bytes, or 48 MiB. At that context the cache is larger than the weights. The limit you choose at export time is memory you pay for on every run. On a phone it is usually the cache, not the weight file, that decides whether your app survives.

09 · 7Verify it, or you have not exported it

An export that loads is not an export that is correct. Silent wrongness is the normal failure mode here: a branch captured on the wrong side, a permute the converter reordered, a quantized operator the backend implemented differently. The model still returns tensors of the right shape. It just returns the wrong numbers.

verify_export.pypython
import torch

exported = ep.module()          # run the captured graph in Python
model.eval()

for T in (1, 7, 128, 200, 511):                 # several shapes, not one
    ids = torch.randint(0, 4096, (1, T))
    with torch.no_grad():
        ref = model(ids)
        got = exported(ids)
    print(T, (ref - got).abs().max().item())
    torch.testing.assert_close(got, ref, atol=1e-5, rtol=1e-5)

That last line hides two different ideas behind two identical-looking numbers. atol is an absolute tolerance: how much raw difference you allow outright. rtol is relative: what fraction of the reference value you allow. The check that runs is:

What assert_close actually tests
| got − ref | ≤ atol + rtol · | ref |

Work one element. Say ref = 12.0, got = 12.00008, with atol = 1e-5 and rtol = 1e-5. The budget is 1e-5 + 1e-5 × 12 = 0.00013. The difference is 0.00008, which is smaller, so it passes. Note what happened: on a logit of size 12, the relative term contributed more than ten times what the absolute term did. On large logits rtol is doing all the work, and on values near zero atol is.

Three rules make this test useful instead of decorative.

Compare against the right reference. An INT4 export compared against an FP32 eager model will always fail, and the failure tells you nothing. Quantize in PyTorch first, then compare the export against that model. Only then is a difference a bug in the export rather than a known cost of Lesson 07.

Test several shapes. One shape only proves that the shape you exported with works. Include the boundaries of your declared range and a length that is not a round number.

When the tolerance stops being meaningful, change the measurement. For a language model, small logit differences are expected and harmless; what matters is whether the generated text is the same, or whether perplexity on a held-out set moved. Compare the argmax token for a few hundred positions, or run the task metric you already have. A number you can defend beats a tolerance you invented.

Worth knowing

Comparing ep.module() against eager PyTorch checks the capture only. It does not check lowering, delegation or the device runtime. Run the same comparison again against the real artefact — through onnxruntime, through the ExecuTorch Python runtime, through Core ML on a Mac — before you believe the export is finished.

The same model, four formats

Take one model through every path in this lesson and write down what each one cost you. The point is not to end with four working files — you will probably not get four. The point is to find out where each path stops.

You do it twice, on the two models from §1.

Warm-up — the tiny GPT of Lesson 04. No adapter to merge, no quantization needed. It is here so that a strange error is an error in code you wrote.

  1. Load the tiny GPT of Lesson 04. Confirm it still generates readable text in eager PyTorch, and save that output to compare against later.
  2. Capture it: torch.export.export with the sequence dimension marked Dim.DYNAMIC. Save the .pt2. Print ep.range_constraints and read what export inferred.
  3. Lower to .pte with XnnpackPartitioner. Record the file size, then run partition_report.py from §5 and copy down all four numbers: total nodes, delegated nodes, non-delegated nodes, and subgraphs.

The one you ship — the model you fine-tuned in Lesson 05. Merged with merge_and_unload() in Lesson 05, quantized to INT4 in Lesson 07, profiled in Lesson 08. This is the artefact Lesson 10 runs on a device and Lesson 13 loads.

  1. Capture and lower it to .pte exactly as above. Run the partition report again. The delegated fraction will be lower than the tiny GPT's — find out which operators were refused, and write them down.
  2. Export to .onnx with dynamo=True and run it through onnxruntime on the CPU execution provider.

Check yourself

You exported with an example of shape (1, 128) and passed no dynamic_shapes. In production the model is called with (1, 64). What happens?

Capture bakes in every shape it observed unless you mark the dimension dynamic. Shorter is not safer than longer — the constraint is equality with 128, not an upper bound.

A model has 8 layers, 6 key-value heads and head dimension 64, at FP16. You are at position 512. Using §6's two formulas, how many bytes does each design move for that one token?

2 × 8 × 6 × 64 × 2 = 12,288 bytes, and that is the whole cost of the state design at any position. The in-and-out design multiplies it by T, so at 512 it moves 6,291,456 bytes — exactly 6 MiB — for one token. That factor is the entire argument of §6.

You need one artefact that runs in an iOS app, in an Android app and in a desktop command-line tool, and your model is an architecture you designed yourself. Which path, and what do you give up?

GGUF is out immediately: llama.cpp must already implement your architecture in C++, and yours is new. Core ML is Apple only. ExecuTorch would also reach all three, but ONNX has the widest execution-provider coverage from one file. The cost is real: the deepest Qualcomm and Neural Engine support lives in the platform-native paths, so you trade peak speed for one artefact.

Your model exports with an NPU partitioner and the export succeeds, but it is slower on the phone than the plain CPU build. What is the most likely cause?

Partial delegation always succeeds, because unclaimed nodes fall back to portable CPU kernels. The cost appears at the borders, and the report tells you how many borders there are: num_delegated_subgraphs, doubled, is your crossings per call. A high delegated fraction spread over many subgraphs is the slow case.

Your INT8 export differs from the FP32 eager model by up to 3e-3 per logit, and your test asserts atol=1e-5, rtol=1e-5 on logits around 10. Does raising rtol to 1e-4 fix it, and what should you do?

Do the arithmetic: the budget is atol + rtol·|ref| = 1e-5 + 1e-4 × 10 = 1.01e-3, which 3e-3 still exceeds. But chasing the tolerance is the wrong move anyway. You are measuring two changes at once — quantization error plus export error. Quantize in PyTorch first and compare like with like, so any remaining difference is genuinely the export's fault.

Key words from this lesson
Eager also: eager execution
Ordinary PyTorch: one operator runs, then Python decides what to do next. The mode export replaces, and the word its error messages assume you know.
Capture also: tracing
Running the model once and writing down every tensor operation it performed.
ExportedProgram
What torch.export returns: one flat graph, the weights, and the rules about which shapes may change.
ATen operator
One of PyTorch's small set of primitive tensor operations. Every backend agrees on their meaning.
Lowering
Rewriting the graph's operators into the narrower set that one particular backend can execute.
Backend
A hardware target plus the code that runs on it — CPU kernels, GPU shaders, an accelerator compiler.
Partitioner
The object you pass at export time. It walks the graph on one backend's behalf and claims the nodes that backend can run, leaving the rest to the CPU.
Delegate island also: island, delegated subgraph
A maximal run of neighbouring operators one backend agreed to take. The run is replaced by a single delegate call, and each of its two borders costs a tensor copy.
NPU neural processing unit
A fixed-function accelerator for neural-network arithmetic, beside the CPU and the GPU on most recent phone chips. Apple's is called the Neural Engine.
Guard
A condition recorded during capture and checked on every call, such as "this dimension equals 128".
Opset
The version number of the ONNX operator vocabulary a file is written in.
Execution provider
ONNX Runtime's name for a backend, such as CPU, Core ML or WebGPU.
Stateful model
A model that owns a buffer between calls, so it can update a cache in place instead of copying it.
Flatbuffer
A binary file layout you read straight from disk, with no parsing step. It is what lets a .pte be memory-mapped instead of loaded.
Tolerance atol and rtol
How large a numeric difference you accept before you call it a bug. atol is a flat allowance; rtol is a fraction of the reference value. A test passes when the difference is at most atol + rtol × |ref|.
