04

Train your own tiny GPT

A language model is not trained on questions and answers. It is trained on one very long stream of text, cut into equal blocks, with a cross-entropy loss at every single position. This lesson turns that sentence into a training run you can afford.

Part II · Language models ≈ 125 min reading Project · A ~15M parameter GPT that writes stories Needs · Lessons 01, 03

By the end you can

  • Write the next-token objective in four lines of PyTorch, and say why the labels are the inputs shifted by one.
  • Turn a folder of documents into packed fixed-length blocks with no wasted compute.
  • Predict the loss at step 0 before you run anything, and diagnose a curve that goes wrong.
  • Use C ≈ 6ND to convert a model shape into a number of hours.
  • Explain why on-device models are deliberately overtrained compared with the compute-optimal point.

04 · 1The objective is one loss, T times

Pretraining has exactly one rule: given the tokens so far, predict the next one. A GPT — a generative pre-trained transformer — is the decoder-only model you built in Lesson 03, trained under that one rule. It sounds like a single prediction per example. It is not. Because of the causal mask from Lesson 03, a block of T tokens produces T predictions in one forward pass, and every one of them is graded.

So the objective is not new. It is Lesson 01's cross-entropy, applied at every position at once, and then averaged into one number so that gradient descent has a single surface to walk down. Three letters carry the shapes for the rest of the lesson: B is the batch size, T is the block length in tokens, and V is the vocabulary size.

One convention, stated once. Every logarithm here is a natural logarithm, so the loss is measured in nats per token. A nat is a bit on base e instead of base 2: one nat is 1/ln 2 ≈ 1.44 bits. That conversion returns in perplexity and in bits per byte.

The labels are the inputs, moved one place to the left. There is no separate label file, no annotation step, no human in the loop. That is the whole reason pretraining scales: the text labels itself.

Two names for the rest of the lesson. x is the block of inputs and y is the same block shifted one place left. The next section builds them; here is what the loss does with them.

objective.pypython
import torch.nn.functional as F

# x, y: (B, T) int64. y is x shifted one place left — see get_batch below.
logits = model(x)                            # (B, T, V)

loss = F.cross_entropy(
    logits.reshape(-1, V),                   # B*T rows, V scores each
    y.reshape(-1),                           # B*T correct token ids
)                                            # one scalar, the mean over every position
The shift that fails silently

Shift the labels the wrong way, or forget to shift them at all, and nothing crashes. The model learns to copy its input, which it can do almost perfectly, so the training loss falls close to 0 within a few hundred steps and the samples are garbage. A loss that drops below about 1.0 in the first thousand steps of pretraining is a bug, not a breakthrough. Print one batch and check by hand that y[0][3] == x[0][4].

Remember this

One forward pass over a block of 256 tokens gives you 255 training signals, not one. This is why attention with a causal mask is so efficient to train, and it is also why the same trick does not work for image classification, where one image gives one label.

04 · 2Data: a corpus, a tokenizer, one long stream

Choose the corpus before the architecture. Here it is TinyStories (roneneldan/TinyStories, licence CDLA-Sharing-1.0, about 480 MB, 2.12 million training rows). It is short children's stories written with a small vocabulary. That matters: on simple text a model of a few million parameters can produce coherent output, which the same model trained on general web text cannot.

If you want the flavour of real web text instead, a good alternative is HuggingFaceFW/fineweb-edu with the config sample-10BT, loaded with streaming=True so you do not download twenty gigabytes. Expect worse samples at this model size: web text is harder than children's stories.

Train the tokenizer first

The token vocabulary is a real engineering choice, not a default to copy. The embedding table has V × d entries, and small models tie the input embedding to the output head, so you pay for it once — but you still pay.

For a model under about 200 million parameters, keep V between 8k and 32k. This project goes smaller still, 4,096, because TinyStories uses a narrow vocabulary and a small V leaves more of the parameter budget inside the layers. As a comparison, nanochat's d20 — the d is depth, so twenty transformer blocks — uses 65,536, chosen so that token ids fit into a uint16.

tokenizer.pypython
from datasets import load_dataset
from transformers import AutoTokenizer

ds = load_dataset("roneneldan/TinyStories", split="train")

old = AutoTokenizer.from_pretrained("gpt2")          # borrow the byte-level byte-pair (BPE) recipe

def corpus_iter(dataset, batch=1000):
    for i in range(0, len(dataset), batch):
        yield dataset[i : i + batch]["text"]

tok = old.train_new_from_iterator(corpus_iter(ds), vocab_size=4096)
tok.save_pretrained("./tiny-tokenizer")

train_new_from_iterator keeps the algorithm and the pre-tokenizer of the old tokenizer and learns new merges on your corpus. It only works on fast, Rust-backed tokenizers, which in transformers v5 is every tokenizer.

Packing, not padding

Documents have random lengths and a batch has to be a rectangle. The naive fix is padding, and padding is pure waste: a padded position costs the same matrix multiply as a real one and contributes nothing to the gradient. Packing concatenates every document into one stream, puts an end-of-text token between them, and cuts the stream into blocks of exactly T tokens.

pack.pypython
import numpy as np

BLOCK, eos = 256, tok.eos_token_id

def encode(batch):
    return {"ids": [x + [eos] for x in tok(batch["text"])["input_ids"]]}

enc = ds.map(encode, batched=True, remove_columns=ds.column_names)

with open("train.bin", "wb") as f:                       # one long stream on disk
    for row in enc:
        np.asarray(row["ids"], dtype=np.uint16).tofile(f)

arr = np.memmap("train.bin", dtype=np.uint16, mode="r")  # never loaded into RAM
n = len(arr) // BLOCK
blocks = arr[: n * BLOCK].reshape(n, BLOCK)              # (n, 256)
print(n, "blocks,", arr.size, "tokens")

Two details in that file are worth naming. uint16 holds ids up to 65,535, so any vocabulary at or below 65,536 halves your disk and your memory-map traffic. And np.memmap means the operating system pages the stream in on demand — you can train on a file larger than your RAM without writing a single line of streaming code.

Run the same pipeline on the validation split into val.bin. Keep the two files completely separate. A validation set that shares documents with the training set will report a loss that is too low, and you will not find out until the samples disappoint you.

From blocks to (x, y)

blocks is still one array. The training loop wants pairs. This is the five-line function that closes the gap, and it is where the label shift lives:

batch.pypython
import numpy as np, torch

def get_batch(blocks, bs, dev):
    idx = np.random.randint(0, len(blocks), bs)          # bs random block numbers
    b = torch.from_numpy(blocks[idx].astype("int64"))    # (bs, 256)
    return b[:, :-1].to(dev), b[:, 1:].to(dev)          # x is 255 tokens, y is the same block shifted left

x, y = get_batch(blocks, 32, dev)
assert (x[0, 1:] == y[0, :-1]).all()                     # the shift, checked once, out loud

Say it once, because three later snippets depend on it: the shift lives in the loader. From here on no loss function slices anything. A 256-token block therefore trains on 255 positions, which is where the "255 training signals" figure comes from.

The random indices are not laziness. Neighbouring blocks come from the same documents, so a batch of neighbours is a batch of one topic.

Worth knowing

This naive cut is called wrapped packing, and it is what classic pretraining does: a document may be cut across a block boundary, and the model simply learns from both halves. For instruction fine-tuning in Lesson 05 that is not acceptable, because cutting an assistant answer in half teaches the model to stop in the middle. There the default is best-fit-decreasing packing, which never splits an example.

04 · 3What one optimizer step really is

Here is the problem this section solves. Your device holds maybe 32 blocks at a time, but pretraining wants tens of thousands of tokens in every step, or the gradient is too noisy to follow. Take small steps anyway and the loss curve is a jagged mess. Two lines of code fix it, and neither is obvious.

So forget batch size for a moment. The number that decides how your run behaves is tokens per optimizer step:

tokens_per_step = micro_batch × T × accum_steps × world_size micro_batch rows on the device at once T block length, in tokens accum_steps backward passes before one step world_size how many GPUs run the same model in parallel; 1 on your machine

Multi-GPU training is out of scope for this course, so world_size is 1 in every number below. For this project: 32 × 256 × 8 × 1 = 65,536 tokens per step. For scale, nanochat's d20 uses 524,288 tokens per step (219) at block length 2,048, and SmolLM3-3B used 2.36 million at block length 4,096.

One bookkeeping note, because section 04·2 was strict about it. This formula counts the tokens read from the stream, not the positions graded. The loader spends one position per block on the shift, so 32 × 255 × 8 = 65,280 positions actually get a loss. That is 0.4% fewer, and every budget number below ignores the difference.

Two runs with the same tokens per step behave almost identically, whatever combination of micro-batch and accumulation produced it. That is the knob to reason about. It is a rule of thumb, not a law: it holds only while the learning rate stays fixed, and only while no layer depends on the micro-batch. Verify it yourself — run micro-batch 64 with ACC = 4 and check that the two curves lie on top of each other.

Gradient accumulation is what makes that possible on one small GPU. Lesson 01 showed that PyTorch adds into .grad instead of replacing it, and called that a bug waiting to happen. Here it is the feature: run several micro-batches, call backward() on each, divide the loss so the sum comes out as an average, and step once. Memory scales with the micro-batch. The effective batch scales with the product.

Gradient clipping is the second line you must not skip. Compute the global L2 norm over every gradient — the square root of the sum of the squares of every gradient in the model. If it is larger than a limit, scale every gradient down by the same factor. The direction is unchanged, only the length is capped.

The maths, once
g ← g × min(1, clip / ‖g‖₂) g all gradients, treated as one long vector clip = 1.0

Once by hand: if the norm is 4.0 and the limit is 1.0, then min(1, 1/4) = 0.25 and every gradient is multiplied by 0.25. A gradient of −3.2 becomes −0.8, one of +0.4 becomes +0.1, and the ratio between them never changes. That is "same direction, shorter".

A limit of 1.0 is what SmolLM3 pretraining used, and it is the default in transformers and in TRL (Transformer Reinforcement Learning, Hugging Face's training library for fine-tuning and alignment, which you will use from Lesson 05 onwards). Without clipping, one corrupt document produces one enormous gradient, every weight jumps, and the loss curve spikes and often never recovers. Log the norm before clipping — that number is your early warning.

04 · 4Warmup, then cosine decay

A constant learning rate is the wrong choice for pretraining, at both ends of the run. At the start the model is random, the gradients are large and badly correlated, and a full-size step throws the weights somewhere useless. At the end you want small steps to settle into a minimum rather than bounce around it.

So the schedule has two parts. Warmup raises the learning rate linearly from near zero over the first few hundred steps. Cosine decay then lowers it smoothly to a floor, usually about one tenth of the peak, over the rest of the run.

The training loop below also carries one line you have not met. Without it, activations are stored in 32-bit and a batch that should fit does not, so it is worth two minutes before the code.

Automatic mixed precision, in one box

Automatic mixed precision (AMP) is what torch.autocast switches on. Inside that block, PyTorch runs the expensive operations in 16-bit — matrix multiplies above all — and keeps the delicate ones in 32-bit: softmax, the normalisation layers, the loss, and the master copy of the weights. Activation memory roughly halves and the matrix multiplies get faster.

The two 16-bit formats are not interchangeable. BF16 has the same exponent range as FP32, so nothing else is needed. FP16's range is far narrower, and small gradients fall below its smallest number and become exactly zero, silently. torch.amp.GradScaler is the fix: it multiplies the loss by a large factor before backward() so the gradients land back inside FP16's range, then divides that factor out before the step. Lesson 07 explains the bit layouts.

train_step.pypython
import math, torch, torch.nn.functional as F

ACC = 8            # micro-batches per optimizer step: 32 x 256 x 8 = 65,536 tokens
TOTAL = 4300       # D // tokens_per_step = 284_000_000 // 65_536 = 4,333, rounded down
WARMUP = 200       # about 5% of TOTAL — a rule of thumb, not a derived number

def lr_at(step, peak=1e-3, floor=1e-4):
    if step < WARMUP:
        return peak * (step + 1) / WARMUP            # linear warmup
    t = (step - WARMUP) / max(1, TOTAL - WARMUP)     # 0 -> 1
    return floor + 0.5 * (peak - floor) * (1 + math.cos(math.pi * t))

opt.zero_grad(set_to_none=True)
for i in range(TOTAL * ACC):
    x, y = get_batch(blocks, 32, dev)                # (B, T) int64, already shifted
    with torch.autocast(device_type=dev, dtype=amp_dtype):
        logits = model(x)                            # (B, T, V)
        loss = F.cross_entropy(logits.flatten(0, 1), y.flatten())
    (loss / ACC).backward()                          # gradients accumulate
    if (i + 1) % ACC == 0:
        step = i // ACC
        for g in opt.param_groups:
            g["lr"] = lr_at(step)
        gnorm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        opt.step()
        opt.zero_grad(set_to_none=True)

Two of those constants have a source and one does not. TOTAL is the training budget divided by the tokens per step, derived in section 04·6. ACC is whatever makes the micro-batch fit in memory. WARMUP is only a rule of thumb — a few hundred steps, or roughly 5% of the run. Nobody derives it; people raise it when the loss spikes.

Use AdamW, as in Lesson 01. amp_dtype depends on your hardware: torch.bfloat16 on Apple Silicon and on modern NVIDIA cards. A free Colab T4 is a Turing chip — NVIDIA's 2018 generation, two generations before BF16 support — so there you need torch.float16 together with torch.amp.GradScaler, exactly as the box above describes.

Common trap

A sharp loss spike a few steps after warmup finishes means the peak learning rate is too high — warmup was hiding it. Lower the peak or lengthen the warmup. Do not respond by lowering the floor; the floor is not the problem.

04 · 5Reading the loss curve by the numbers

The loss is mean cross-entropy in nats per token, and you can predict its very first value before you run anything. A freshly initialised model is close to uniform over the vocabulary, so it assigns probability 1/V to the correct token, and −ln(1/V) = ln(V). With V = 4,096 that is ln(4096) = 8.32, and you can check it on a calculator right now.

Perplexity, and where it stops helping

Perplexity is exp(loss). It has a useful reading: roughly how many equally likely tokens the model was choosing between. A model at loss 8.32 over a 4,096-token vocabulary has perplexity 4,096 — it has learned nothing yet. At loss 2.0 the perplexity is 7.4.

evaluate.pypython
import math, torch, torch.nn.functional as F

@torch.no_grad()
def val_loss(model, blocks, bs=16):
    model.eval()
    total, n = 0.0, 0
    for i in range(0, len(blocks), bs):
        b = torch.from_numpy(blocks[i : i + bs].astype("int64"))
        x, y = b[:, :-1].to(dev), b[:, 1:].to(dev)   # the same shift as get_batch
        logits = model(x)
        l = F.cross_entropy(logits.flatten(0, 1), y.flatten())
        total += l.item() * x.size(0)
        n += x.size(0)
    model.train()
    return total / n

l = val_loss(model, val_blocks)
print(f"val loss {l:.3f}   perplexity {math.exp(l):.1f}")
Perplexity is not a leaderboard

Perplexity is only comparable between models that use the same tokenizer and the same evaluation text. A model with a larger vocabulary produces fewer tokens for the same sentence, so its per-token loss is spread differently, and the two numbers cannot be compared. To compare across tokenizers, use bits per byte: bpb = (loss × n_tokens) / (ln 2 × n_bytes). It is measured per byte of the original text, so the tokenizer cancels out. The division by ln 2 is the nats-to-bits conversion from section 04·1: multiplying by 1/ln 2 ≈ 1.44 turns a nat into a bit. Multiplying by n_tokens and dividing by n_bytes moves the "per" from tokens to bytes.

04 · 6How many tokens? Scaling laws, and why you overtrain

Without this section you start a run and find out how long it takes by waiting. That is fine for one afternoon and fatal for a budget. Two formulas replace the waiting with arithmetic you can do before you type anything.

The maths, once
C ≈ 6 × N × D D* ≈ 20 × N C training compute, in FLOPs N non-embedding parameters D training tokens D* the compute-optimal choice of D

The 6 is two FLOPs — floating-point operations — per parameter per token in the forward pass, plus four in the backward pass. The D* ≈ 20N rule comes from Chinchilla (Hoffmann et al., 2022), which trained 70 billion parameters on 1.4 trillion tokens and beat a 280-billion model on the same compute budget.

The whole sum, for this project

Every number is on this page. Follow it with a calculator.

  1. N = 14.2 M non-embedding parameters, from the project table below.
  2. D* = 20 × 14.2e6 = 284 M tokens. At 65,536 tokens per step that is 284e6 ÷ 65,536 = 4,333 steps, which we round to TOTAL = 4300 — 282 M tokens. That is where the constant in train_step.py comes from.
  3. C = 6 × 14.2e6 × 282e6 = 2.4e16 FLOPs.
  4. A free Colab T4 is quoted at 65 TFLOP/s in FP16. That is the marketing number. This model sustains about 5% of it, which is 3.3 TFLOP/s — the next callout says why.
  5. 2.4e16 ÷ 3.3e12 = 7,300 seconds ≈ 2 hours. Compare that with the 1.5 – 3 h row in the wall-clock table below. They agree, because the table was built from this sum.

That is the whole worksheet, and it transfers. For any other model: pick N from your memory budget, pick D (floor 20N, on-device target 500 to 2,000 tokens per parameter), compute 6ND, divide by your measured FLOPs per second, and multiply by the price per second to get the invoice.

Why 5% and not 40%

You will read that a well-tuned run reaches 35% to 45% of a GPU's peak FLOPs. That figure is real, and it is for a large model on a data-centre card. Your 15 M-parameter model with 256-token blocks is a different animal. Its matrices are small, so each kernel finishes before the GPU is properly busy, and the run is dominated by launching kernels rather than by arithmetic. A few percent of peak is normal there.

The part that generalises: utilisation is a property of the shape, not of the chip. Measure it once on your own model — time 50 steps, multiply tokens by 6N, divide by seconds — and reuse your own number.

Chinchilla answers a specific question: given a fixed training budget, what is the best model? That is the right question for a lab that trains once and then serves from its own data centre. It is the wrong question for a model that ships to a phone.

If your model runs on a device, you pay training cost once and inference cost millions of times. Every hour you add to training makes every future generation cheaper, because a smaller, longer-trained model beats a larger, briefly-trained one at the same quality. So you deliberately train far past the compute-optimal point.

Our project sits at the Chinchilla point, not past it, for one reason only: you have to be able to finish it today. Its 282 M tokens are 20 per parameter. The overtraining regime is what a team with more GPU time would do with exactly the same code — and the fourth self-check question at the end of this lesson makes you price two days of it.

04 · 7Generation: choosing one token

Training is finished. Now the model produces logits over V tokens at the last position, and something has to pick one. That choice is not part of the model, it costs nothing, and it changes the output more than another hour of training would.

One notation warning first. The letter T is already taken in this lesson: it is the block length, from the tokens-per-step formula onwards. Sampling temperature is therefore written τ here, and temp in the code. They are the same knob.

MethodWhat it doesTypical valueWhen it hurts
GreedyTake the highest logit every time—Repeats itself, gets stuck in loops
TemperatureDivide the logits by τ before softmaxτ = 0.6 – 0.7High values make the model wander off topic; near 0 it becomes greedy
Top-kKeep the k highest logits, discard the rest, renormalisek = 20k is fixed, so when the model is certain it still admits k−1 wrong answers
Top-pKeep the shortest list whose probabilities reach pp = 0.8 – 0.95Rarely; it adapts to the model's confidence. This is the default to reach for
Beam searchKeep the k best whole sequences so far, ranked by total log-probability, and extend all of themk = 4 – 8k times the compute, and bland text — but it is standard in speech recognition, where there is one right answer. Lesson 11 uses it

Top-p, also called nucleus sampling (arXiv:1904.09751), is the one that adapts. When the model is sure, the list is one token long. When it is unsure, the list grows. Top-k cannot do that, because k is a constant. In practice people combine them: a temperature, then top-p, and often a generous top-k as a safety net.

generate.pypython
import torch

@torch.no_grad()
def generate(model, ids, n=120, temp=0.7, top_k=None, top_p=0.9):
    cache = None
    for _ in range(n):
        step_ids = ids if cache is None else ids[:, -1:]    # prefill, then decode
        logits, cache = model(step_ids, cache=cache)        # see cache_attention.py
        z = logits[:, -1] / temp                            # (B, V); temp is the tau above
        p = torch.softmax(z, dim=-1)

        if top_k:                                           # top-k, three lines
            v, _ = torch.topk(p, top_k, dim=-1)             # v[..., -1] is the k-th largest
            p = torch.where(p < v[..., -1:], torch.zeros_like(p), p)
            p = p / p.sum(-1, keepdim=True)                 # renormalise, or top_p below cuts
                                                            # 90% of whatever top-k left

        srt, idx = torch.sort(p, descending=True, dim=-1)
        # cumsum minus self = the probability mass strictly BEFORE this token.
        # For the first token that mass is 0, so it always passes, whatever top_p is.
        keep = (srt.cumsum(-1) - srt) < top_p
        srt = torch.where(keep, srt, torch.zeros_like(srt))
        pick = torch.multinomial(srt / srt.sum(-1, keepdim=True), 1)
        ids = torch.cat([ids, idx.gather(-1, pick)], dim=1)
    return ids
Moved in transformers v5

When you use a Hugging Face model rather than your own, the sampling settings live on model.generation_config, not on model.config. That moved in v5. Setting them on config now does nothing at all, silently, and you will spend an hour wondering why temperature has no effect.

04 · 8Prefill and decode are two different machines

Look again at the loop above. The first iteration passes the whole prompt; every iteration after that passes exactly one token. That is not an optimisation detail, it is two different workloads with two different bottlenecks.

The reason it works is the causal mask. The keys and values computed for position 7 can never depend on position 8, so once you have them they are final. Store them and you never compute them again. That store is the key-value cache, almost always written KV cache.

Prefill

  • The whole prompt in one forward pass.
  • Large matrix multiplies, many rows at once.
  • The chip is doing arithmetic — compute-bound.
  • You measure time to first token.
  • A longer prompt costs more here, and only here.

Decode

  • One token per pass, forever.
  • Every weight in the model is read to produce one token.
  • The chip is waiting for memory — memory-bound.
  • You measure tokens per second.
  • Halving the bytes per weight roughly halves the time per token.

That last line is the whole argument for Lesson 07. Quantization does not make the arithmetic faster; it makes the weights smaller, and during decode the weights are what you are waiting for.

Building the cache

The model you wrote in Lesson 03 takes no cache and returns none, so model(step_ids, cache=cache) above fails on the first call until you add six lines to the attention block. Here they are.

cache_attention.pypython
# inside attention, after q, k, v are projected and reshaped to
# (B, H, T, head_dim) -- H query heads, head_dim the width of one head

past_len = 0 if cache is None else cache[0].shape[2]     # how many tokens are already stored
q = rope(q, offset=past_len)                             # position of this token in the WHOLE sequence
k = rope(k, offset=past_len)

if cache is not None:
    k = torch.cat([cache[0], k], dim=2)                  # dim 2 is time: old keys, then new
    v = torch.cat([cache[1], v], dim=2)

new_cache = (k, v)                                       # hand this back to the caller
out = F.scaled_dot_product_attention(q, k, v, is_causal=(q.shape[2] > 1))

Two traps live in those six lines, and neither one raises an error.

The time axis. Keys and values are shaped (B, H, T, head_dim), so the concatenation must be on dimension 2. Concatenate on the head axis instead and the shapes still work out, while the model quietly grows heads and generates confident nonsense.

Rotary position embedding (RoPE) offsets. During decode you pass one token, so its position inside its own tensor is 0 — but its real position is past_len. Apply RoPE at 0 and every generated token believes it is the first word of the text. The output stays grammatical and stops holding together across a sentence.

The mask needs no new code. During prefill the query length equals the key length, so Lesson 03's causal mask applies unchanged. During decode there is one query against past_len + 1 keys, and one query may legally see all of them — which is why is_causal is off when the query length is 1.

Cache size, exactly
bytes = 2 × layers × kv_heads × head_dim × tokens × bytes_per_element

kv_heads is Lesson 03's G, the number of key/value groups, and head_dim is its d_h, the width of one head. Same two quantities, spelled out.

For this lesson's model — 8 layers, 6 key-value heads, head dimension 64, FP16 at 2 bytes per number — that is 2 × 8 × 6 × 64 × 2 = 12,288 bytes, or 12 KiB per token, so a full 256-token context costs 3 MiB. The same formula on a real 1-billion-parameter model, and the grouped-query attention that shrinks it, is worked through in Lesson 03 §5. On a phone the cache, not the weights, is often the real memory limit.

A ~15M parameter GPT that writes stories

Take the transformer block you wrote in Lesson 03 and train it, from random weights, until it writes short stories that stay on topic. Nothing here is a toy version of the real thing: the pipeline below is the same one that produced every model in this course, only smaller.

Two things change from Lesson 03, and the parameter count changes with them. Stack eight of those blocks now, not six. And use the 4,096-entry tokenizer you trained in section 04·2, not Lesson 03's 8,192 or the 65-character vocabulary of its project. The block itself is untouched, so its 1,770,240 parameters are the same number Lesson 03 §8 printed. Six blocks on 65 characters came to 10.65 M. Eight blocks on 4,096 tokens come to 15.7 M, and that is the model the rest of this lesson budgets for. Lesson 09 loads this one, so use these numbers.

Be clear about what this model is for. It is the model you understand completely, and it is not the brain of the capstone assistant. That job goes to the open instruct model you fine-tune in Lesson 05, which Lessons 07 to 10 quantize, profile, export and run. Your tiny GPT reappears once, in Lesson 09, as the warm-up export.

  1. Train a 4,096-entry BPE tokenizer on TinyStories and save it.
  2. Pack the train and validation splits into two uint16 stream files, and cut them into 256-token blocks.
  3. Build the model: 8 layers, d_model 384, 6 heads, SwiGLU with d_ff 1024, RMSNorm, RoPE, tied embedding. Print the parameter count and check it against the table.
  4. Train with AdamW for 4,300 optimizer steps at 65,536 tokens per step — 282 M tokens, which is 20 per parameter. Clip gradients at 1.0, warm up over 200 steps, then cosine decay from 1e-3 to 1e-4.
  5. Log loss, grad_norm and tokens seen. Sample 100 tokens from the prompt "Once upon a time" every 500 steps and paste the samples into your notes.
  6. Add the cache to your attention block (cache_attention.py above), then write the sampler around it. Report validation loss and perplexity at the end.

Then break it on purpose. Each of these produces a different, recognisable failure, and recognising them is worth more than the trained model:

  • Remove the label shift. How many steps until the loss is under 0.1, and what do the samples look like then?
  • Set max_norm=1000.0 so clipping never fires. Watch grad_norm.
  • Set WARMUP = 0. What happens in the first 50 steps?
  • Generate at temperature 0.1 and at temperature 2.0 from the same checkpoint.

Then measure it. Time the prefill of a 256-token prompt, then time 256 decode steps, and divide both by the number of tokens. Call torch.mps.synchronize() or torch.cuda.synchronize() before every perf_counter() — without it you are timing the queue, not the work. The per-token cost of the two phases will differ by more than an order of magnitude, and Lesson 08 is about that gap.

Try it

Before you start the long run, do the overfit test from Lesson 01 in its language-model form: take one block of 256 tokens and train on that block alone. A correct training loop drives the loss to nearly zero within a minute or two, and the model will then recite that block back to you word for word. If it cannot, the bug is in your code and no amount of data will hide it.

Check yourself

You retrain the tokenizer at vocab_size=16384, build a fresh model, and print the loss on the first batch before any optimizer step. What should it be?

A random model spreads its probability evenly over V tokens, so the correct token gets 1/V and the loss is −ln(1/V) = ln(V). 16,384 is 214, so ln(16384) = 14 × ln 2 = 14 × 0.693 = 9.70. Quadrupling the vocabulary adds ln 4 = 1.39 to the starting loss. 16,384 itself would be the perplexity.

Your pretraining loss reaches 0.04 after 300 steps and the generated text is nonsense. What is the most likely cause?

Copying the input is a task the model can solve almost perfectly, so the loss collapses. Real next-token prediction on natural text never reaches such a low loss. Check that y[b][t] == x[b][t+1] on a printed batch.

After the prompt "Once upon a", your model gives the token "time" a probability of 0.94. You are sampling with top_k=3 and, separately, with top_p=0.8. What is the difference?

k is a constant, so top-k admits two unlikely tokens even when the model is certain. Top-p stops as soon as the cumulative probability reaches p, which here happens at the first token. That adaptivity is why top-p is the better default.

You keep the same 14.2 M non-embedding parameters but decide to overtrain, at 500 tokens per parameter instead of 20. Your T4 sustains 3.3 TFLOP/s on this model. Roughly how long is the run?

D = 500 × 14.2e6 = 7.1e9 tokens. C = 6 × 14.2e6 × 7.1e9 = 6.05e17 FLOPs. Divide by 3.3e12 FLOP/s and you get 1.8e5 seconds, which is about 51 hours. Nothing gets cheaper per token: compute is exactly linear in D, so 25 times the tokens is 25 times the 2-hour run. That is the trade small-model teams actually make.

Key words from this lesson
Next-token objective also: causal language modelling, autoregressive generation
Predict the token that follows, at every position of the block at once, and average the losses. A model that generates by feeding its own output back in is called autoregressive; Lessons 11 and 12 use that word for the same behaviour.
Nat
The unit of a loss measured with natural logarithms, as every loss in this course is. One nat is 1/ln 2 ≈ 1.44 bits.
Tokens per optimizer step
micro_batch × T × accum_steps × world_size. The one number that decides how a run behaves; the split between the factors is yours to choose.
Automatic mixed precision AMP
Running the matrix multiplies in 16-bit while keeping the master weights and the loss in 32-bit. FP16 also needs a GradScaler; BF16 does not.
Packing
Joining documents into one stream with a separator token, then cutting it into equal blocks so no position is wasted.
Gradient accumulation
Running several small batches and adding their gradients before one optimizer step, to get a large effective batch on a small device.
Gradient clipping
Capping the total length of the gradient vector while keeping its direction, so one bad batch cannot destroy the weights.
Warmup
Raising the learning rate from near zero over the first few hundred steps, before the real schedule starts.
Cosine decay
Lowering the learning rate along a cosine curve from its peak to a small floor over the rest of the run.
Tokens per parameter
Training tokens divided by parameters. About 20 is compute-optimal; on-device models go far higher on purpose.
Prefill
The first forward pass, which processes the whole prompt at once and fills the cache. Limited by arithmetic speed.
Decode
Every pass after prefill, producing one token at a time. Limited by memory bandwidth.
Bits per byte bpb
Loss measured per byte of original text instead of per token, so two models with different tokenizers can be compared.
