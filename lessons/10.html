On the device

A model file is not a product. Somebody has to open it, place it in memory, pick a chip to run it on, and pay for all of that while a person is watching a loading spinner. This lesson is about that last hundred metres, on two targets: an iPhone app and a browser tab.

By the end you can

  • Say exactly what goes into an app bundle, and why the weights should usually not be one of those things.
  • Explain how a runtime decides which operator runs on the CPU, the GPU or the Neural Engine, and what a fallback costs.
  • Break a cold start into three measured parts and fix the one that actually dominates.
  • Ship a model into a browser tab with caching, and know why the first visit is slow and the second is not.
  • Predict when the operating system will evict or terminate your app, and design the context length around it.
  • Decide when the platform's own model beats shipping your own, and run a licence check before release.

10 · 1Two targets, and the real reason

In Lesson 09 you turned one PyTorch model into four files: a .pte, an .onnx, a .mlpackage, a .gguf. Each is a frozen graph plus its weights, and none of them does anything alone. Each needs a small C++ runtime that opens the file, allocates buffers, and talks to the chips inside the device.

This lesson covers two places that runtime can live:

An iOS app

  • You control the whole bundle: code, runtime library, model file.
  • Real access to the GPU and the Neural Engine.
  • Hard limits: download size, RAM budget, no fan.
  • A review process and a signed binary between you and the user.

A browser tab

  • No install, no store, no review. A URL is the whole distribution.
  • The GPU through WebGPU, the CPU through WebAssembly.
  • The weights arrive over the network on the first visit.
  • You get whatever browser and machine the user happens to have.

People ask for both for the same reason, and it is not cost. It is privacy. A voice memo, a medical note, a photo of a passport — these are things users and legal departments do not want to send to a server. "The data never leaves the device" is a claim you can make truthfully only if the model is on the device. Offline operation and low latency are real too, but they are the second and third reason.

Remember this

On-device inference is a distribution problem wearing a machine-learning costume. The maths was finished in Lesson 07. What is left is bytes on disk, bytes over the network, bytes in RAM, and milliseconds before the first token.

One question comes before all of this, and it is cheap to ask: does the operating system already ship a model that is good enough? Recent phones often do, and a system model costs your app zero bytes. You ship your own for four reasons: a specific fine-tune, a modality the platform does not cover, old devices, or identical behaviour everywhere. Section 8 works that decision through. The rest of the lesson assumes you made it.

10 · 2What is actually inside the app

An iOS app is a folder with a signature. Three things in it matter to us.

Your code. Swift, the interface, images, strings. For an app whose point is one model, this is small.

The runtime library. The C++ engine that reads the model file and executes it: ExecuTorch, ONNX (Open Neural Network Exchange) Runtime, Core ML, or llama.cpp. A build decision pays off here. ONNX Runtime Mobile offers a minimal build: you compile only the operator kernels your own models need. That is the difference between tens of megabytes of binary and a few.

The model file. This is the download. A 360-million-parameter model is 1.44 GB in FP32, 720 MB in BF16, 360 MB in INT8, and about 200 MB at 4 bits with group scales. The file you exported in Lesson 09 is 191 MB. This lesson says 200 MB throughout, because that is the round number every later sum uses. Even after Lesson 07, it dwarfs everything else in the bundle.

The limit is real and it is close. Apple restricts App Store downloads above 200 MB over a cellular connection, and Google Play caps an Android App Bundle's base module at roughly the same size. A 200 MB model plus an app does not fit.

The answer is the same on both platforms: do not put the weights in the binary. Ship a small app. On first run, download the model file, verify a hash so a corrupted or substituted file cannot reach your runtime, and write it into a cache directory. Apple's store-side version of this is called on-demand resources. Either way the weights travel separately from the code.

ModelStore.swiftswift
// Where the weights live decides your app size and who is allowed to delete them.

// (a) Inside the bundle: always present, counts against the download limit.
let bundled = Bundle.main.url(forResource: "model", withExtension: "pte")

// (b) Downloaded once: small app, but the OS may reclaim this at any time.
let caches = FileManager.default
    .urls(for: .cachesDirectory, in: .userDomainMask)[0]
    .appendingPathComponent("model.pte")

let haveModel = FileManager.default.fileExists(atPath: caches.path)
Common trap

A cache directory is not storage you own. iOS deletes files there when the device runs low on space, silently, while your app is not running. If your code treats a missing model file as an unexpected error, some users will see a permanently broken app. Treat "the model is gone" as a normal state with a normal recovery path: show the download screen again.

10 · 3Which chip runs which layer

Pick the wrong chip and you pay twice: the answer is slower and the battery drains faster, and neither shows up as an error. So it is worth knowing who decides.

A phone has three processors that can do matrix arithmetic. The CPU is general and always available. The GPU is wide and good at large regular work. The third is Apple's Neural Engine, an NPU — a neural processing unit, a chip that does only the arithmetic neural networks need. It is fixed-function: it runs a restricted set of operators very fast, and it uses far less power per operation than the other two.

You do not choose per operator. You give the runtime a priority list — with coremltools that is ComputeUnit.CPU_AND_NE, with ExecuTorch it is the partitioners you pass to to_edge_transform_and_lower. The runtime then walks your graph and asks each backend "can you take this node?". A run of accepted nodes becomes a delegate: a slice of the graph one accelerator agreed to run, called from the CPU as a single opaque step. The CPU hands over a tensor and gets a tensor back. Everything refused stays on portable CPU kernels.

The Neural Engine has conditions. It is built around FP16: an operator that forces FP32 falls back to the GPU or the CPU. It prefers four-dimensional tensors laid out as (B, C, 1, S), so unusual ranks push work off it. A model that "runs on the Neural Engine" is in practice three to ten delegated islands with CPU glue between them, and every boundary costs a copy of the tensor.

Common trap

Asking for the Neural Engine at export time is not evidence that it ran. The failure is silent: the model gives correct output and is slower than the plain CPU build, because one unsupported operator in every transformer block split the graph. Dump ExecuTorch's partition report, or open the Core ML Instrument in Xcode and see which unit each region actually used.

Speed is not the only reason to care. The Neural Engine's advantage is energy per token as much as time per token. On a device with a battery and no fan, that is often the number a product decision rests on.

10 · 4Cold start has three parts

"The app takes three seconds to answer the first question" is not a bug report you can act on. Start-up is three separate costs with three separate fixes, and only one of them is usually large.

Open and map the file. Both .pte and GGUF — GPT-Generated Unified Format — are designed to be memory-mapped. The runtime asks the operating system to put the file's bytes in its address space instead of reading them into a buffer. Nothing is copied, and pages arrive from storage the first time a weight is touched. That is why a multi-gigabyte model "loads" in milliseconds.

Compile the model for this device. This is the expensive one. A .mlpackage becomes an .mlmodelc the first time it is loaded, a WebGPU backend compiles shaders, a compiler-based runtime generates kernels. For a large model that is seconds, not milliseconds.

Prefill the prompt. Running the prompt through the model once to fill the key-value (KV) cache. It grows with prompt length, and it is real work you can shorten but not remove. Prefill is the one part of generation that is compute-bound: the whole prompt goes through in one wide batch. That is why an accelerator helps here. Decoding one token at a time is memory-bound, and gains nothing from the Neural Engine.

These are the shape of a real measurement on one device with one model, not a universal figure. But the ratio is the lesson: the fix for cold start is caching compilation, not faster storage.

Here is that fix in full, because "cache the artifact" is doing a lot of work in one table cell. On Apple platforms the compiled form of a .mlpackage is a directory called .mlmodelc, and you can build it yourself.

ModelCompile.swiftswift
import CoreML

// Application Support survives. The caches directory does not.
let support = try FileManager.default.url(
    for: .applicationSupportDirectory, in: .userDomainMask,
    appropriateFor: nil, create: true)
let compiled = support.appendingPathComponent("model.mlmodelc")

if !FileManager.default.fileExists(atPath: compiled.path) {
    // This is the 2 400 ms. It writes into a temporary directory
    // that the system is free to delete, so move the result out.
    let tmp = try MLModel.compileModel(at: packageURL)
    try FileManager.default.moveItem(at: tmp, to: compiled)
}

let model = try MLModel(contentsOf: compiled)   // every later launch: tens of ms

Two details decide whether this works. First, compileModel returns a URL in a temporary directory that the system may empty before your next launch. If you do not move the result, you recompile on every launch. Second, put it in Application Support, not caches. Caches is the directory iOS reclaims under pressure — right for the weights, wrong for this.

A browser gives you no equivalent call. You cannot compile the GPU shaders yourself and store them; whether they are kept is the browser's decision. That is why section 5 tells you to measure the second visit rather than assume it.

Common trap

Measuring cold start twice in a row measures a warm page cache and a warm compilation cache, so you report a number no first-time user sees. Reboot the device, or delete the app's caches, before timing the first launch. Then report both numbers and label which is which.

Keeping a model warm is the other half. Hold the handle for as long as the user might come back. When iOS terminates a background app, everything in memory goes with it: the mapping, the compiled artifact, the KV cache. The next launch is cold again — unless you wrote that artifact to disk.

10 · 5The browser path

A browser tab has no bundle. Nothing to install, nothing to review — that is the whole appeal. The price is that the weights arrive over the network the first time somebody opens your page.

The library for this is Transformers.js, published as @huggingface/transformers. Version 4 rewrote the WebGPU runtime in C++ with the ONNX Runtime team, and covers roughly 200 model architectures. It is Apache-2.0 licensed. The pinned version for this course is 4.2.0.

embed.jsjavascript
// npm i @huggingface/transformers@4.2.0
import { pipeline } from "@huggingface/transformers";

const pipe = await pipeline(
  "feature-extraction",
  "onnx-community/all-MiniLM-L6-v2-ONNX",
  { device: "webgpu", dtype: "q4f16" }
);

const out = await pipe("hello world", { pooling: "mean", normalize: true });
console.log(out.dims);      // [1, 384]

That returns one vector of 384 numbers for the whole sentence — a sentence embedding. It is not Lesson 03's embedding table, which looks up one stored row per token id. This vector is computed: the model runs over every token, and pooling: "mean" averages the results into one. out.dims prints [1, 384]: one input, 384 dimensions. We start here rather than with generation because this model is 20 MB, it runs in a second, and a wrong shape is obvious.

Two arguments carry all the weight. device chooses the backend — "webgpu" for the GPU. dtype chooses which quantized weight file to download: fp32, fp16, q4 or q4f16. Changing dtype changes how many bytes the user downloads, which here is a product decision, not a tuning knob.

The downloaded files go into the browser's Cache Storage, keyed by URL, once per origin rather than once per visit. The second visit resolves the same URLs from disk and sends nothing over the network. This is the most important thing to get right in a browser deployment. It is also what makes your own testing misleading: after the first run, your machine sits permanently in the good case.

Worth knowing

Design the first visit as a real screen, not a spinner. Show the byte count and the progress, and let the user start it deliberately. 200 MB arriving without warning on a metered connection is a complaint, not a feature. Convert it to the unit a user feels: 200 MB is about 160 seconds on a 10 Mbit/s mobile connection, and about 32 seconds on 50 Mbit/s Wi-Fi.

Browsers can evict Cache Storage under storage pressure, exactly as iOS empties a caches directory. Same rule: a cache miss is a normal state. And note what is not promised. Your code caches the weights; whether the compiled shaders are kept is the browser's business.

10 · 6WebGPU and WebAssembly

There are two ways to multiply matrices in a page, and they are not close.

WebAssembly runs the arithmetic on the CPU. It has SIMD everywhere — single instruction, multiple data: one CPU instruction does the same multiply on four or eight numbers at once. That is why the CPU path is slow rather than hopeless. It can also use several worker threads. Threads require SharedArrayBuffer, which requires the page to be cross-origin isolated, which requires two response headers from your server: Cross-Origin-Opener-Policy (COOP) and Cross-Origin-Embedder-Policy (COEP).

WebGPU hands the same work to the GPU as one dispatch of many parallel invocations. It is what made in-browser transformer inference practical. As of January 2026 it is Baseline: the web platform's label for a feature that works in the current version of every major browser. Today that means Chrome and Edge, Firefox 141, and Safari 26.

capabilities.jsjavascript
// Two lines that explain most "why is it slow in production" reports.
console.log(!!navigator.gpu);        // false  -> no WebGPU, you are on the WASM path
console.log(crossOriginIsolated);    // false  -> no SharedArrayBuffer, so ONE wasm thread

// The two response headers that make crossOriginIsolated true:
//   Cross-Origin-Opener-Policy: same-origin
//   Cross-Origin-Embedder-Policy: require-corp
Common trap

Your development server sets those headers; your production host or content delivery network (CDN) does not. Nothing breaks. Threads are disabled and the page falls back to one WebAssembly thread. Inference then slows by roughly the number of worker threads you lost — four to eight on current devices, and a rule of thumb to measure rather than a constant. Nothing appears in the console, so log crossOriginIsolated in production and put it in your telemetry.

What about WebNN, the browser API for talking to an NPU directly? It is still moving. The specification has taken over a hundred substantive changes since 2024, and Chrome exposes it only behind an origin trial. Plan for WebGPU now.

10 · 7Memory, eviction, battery and heat

A phone does not give your app all of its RAM. Each app gets a device-dependent budget, and an app that exceeds it is not slowed or swapped out — it is killed. The mechanism has a name: iOS calls it Jetsam, and it leaves a jetsam event in the crash logs, which is how you confirm the cause. On a 6 GB phone a foreground app may safely hold about 2 to 3 GB.

Until now the running example was a 360-million-parameter model at 4 bits, about 200 MB. That is the easy case. Take instead the largest model that could plausibly fit: 3 billion parameters at 4 bits with group scales. That is the 1.83 GB file you profiled in Lesson 08. The rest of this section uses it.

The distinction that decides your fate is clean versus dirty. Weights you memory-mapped from a file are clean, file-backed pages: a copy already exists on disk, so under pressure the system drops them and reads them again later. That costs latency. The KV cache is the opposite — dirty anonymous memory that exists nowhere else, so it can only be kept or lost with your process.

This is why mmap keeps appearing in this course, and it is a second reason — after the cold-start argument — to prefer runtimes and formats built around it.

Now the sum this whole section exists for. Your context length is whatever is left after everything else has taken its share.

What takes the memorySize

Lesson 08 worked out what one token costs in the cache, for exactly this model: 32 layers, 8 key/value heads, head dimension 128, cache kept in FP16. That is 2 × 32 × 8 × 128 × 2 = 131 072 bytes, about 131 kB per token. So 0.42 GB divided by 131 kB is about 3 200 tokens. That is where the app dies, not what you ship. Leave a margin for a phone that is also running other apps, and ship 2 048 — 0.27 GB of cache.

Notice how small that is beside the numbers a model advertises. Lesson 08 measured the same cache at 8 192 tokens and got 1.07 GB, more than twice the headroom you have here. A 32 768-token context window is a property of the model, not a promise your phone can keep.

Remember this

On a phone, maximum context length is a memory setting, not a product setting. In Lesson 04 the KV cache was a speed optimisation. Here it decides whether the operating system terminates your app mid-conversation. Cap it, and free it when you move to the background.

The project asks you to raise the context length until the app is terminated. That step verifies the 3 200; it is not how you discover it. Predict first, then measure. A prediction that misses by a factor of two means you forgot something in the table.

Two more physical limits, both from Lesson 08 and both worse on a phone than on a laptop.

Heat. There is no fan. Sustained inference raises the die temperature, and the system reduces clock speeds after roughly 30 to 120 seconds. So a ten-second benchmark reports a number your users see for ten seconds. Report sustained throughput over five minutes, and give background work a duty cycle.

Battery. Generation is memory-bound: each token reads every weight once and does very little arithmetic per byte. Moving bytes costs energy. Halving the bytes per weight roughly halves both the time per token and the energy per token. That is why 4-bit is the default on device, and why "INT8 is fast enough on the server" does not transfer.

10 · 8When the best model is one you do not ship

In 2026 the first question is no longer "which runtime?". It is "does the operating system already ship a model that is good enough?" Section 1 raised it. Here is the answer in detail.

On Apple platforms, the Foundation Models framework gives you an on-device model of roughly three billion parameters. It is free, offline, and needs no API key. It can also return a typed object instead of free text: @Generable is a Swift annotation on a struct, and the model must fill that struct in. Apple publishes a toolkit for training rank-32 LoRA (low-rank adaptation) adapters for it — Lesson 05's technique, on a model you never downloaded.

The same framework offers a larger model with a 32-thousand-token context, running under Private Cloud Compute. Read that carefully: the request leaves the phone for Apple's servers. The encryption story is unusually strong, but this option cannot carry the privacy claim from section 1. If "the data never leaves the device" is your promise, it is not for you.

On Android, the equivalent is ML Kit's GenAI APIs over AICore. AICore is a system service that hosts Gemini Nano and exposes prompting, summarization, proofreading, rewriting and image description. It runs on recent MediaTek, Qualcomm and Google Tensor devices.

In both cases the operating system shares one model, so it costs your app zero bytes of download. Compare that with the 200 MB you were about to ask a user to accept.

You ship your own model when you need one of these four things:

  1. A specific fine-tune, or behaviour the platform model will not produce.
  2. A modality the platform does not cover — your own speech, audio or vision model.
  3. Guaranteed availability on older or cheaper devices that have no system model.
  4. Identical behaviour across iOS, Android and the web, from one artifact.

The shipping checklist

Before a build with a model in it leaves your machine, work through this. Every item here is something that has shipped broken.

  1. Licence of the weights. Read the model card and the repository licence, not the blog post. Apache-2.0 and MIT are safe in a closed app. A copyleft licence — GPL-3.0 and its relatives — asks anyone who distributes the software to publish their own source under the same terms. That is why copyleft rarely survives a closed app. The Piper text-to-speech (TTS) project is GPL-3.0, and that is a decision your legal team makes, not you.
  2. Gating. Some models are gated on the Hugging Face Hub: you must accept terms with an account before the files download. A gated model cannot be fetched by your continuous-integration (CI) build or by your users' devices without credentials. Check before you build a product on it.
  3. Licence of the training data, when you trained the model yourself. TinyStories is CDLA-Sharing-1.0; CIFAR-10's card says the licence is unknown. Record what you used.
  4. Download size measured on a clean install, against the 200 MB cellular limit.
  5. Cold start after a reboot, reported as three numbers, not one.
  6. Peak memory at your maximum context length, measured with Instruments, with headroom left over.
  7. Sustained throughput over five minutes, not ten seconds.
  8. The cache-miss path. Delete the model file while the app is closed, then launch. Do the same in a browser with cleared storage.
  9. The no-WebGPU path, and crossOriginIsolated in production.
  10. Output check. Run the same ten prompts through the PyTorch model and the exported one. Quantization and delegation both change numerics.

Project 10

Your model, in an app you can hold

Take the model you fine-tuned in Lesson 05 and exported in Lesson 09, and make it run somewhere a person can touch it. The browser track is required, because everybody can do it. The iOS track is the second half if you have a Mac and Xcode. There is no training here — the work is measurement and honesty.

  1. Serve the page. Install @huggingface/transformers@4.2.0 and build a one-page application that loads a model with { device: "webgpu", dtype: "q4" }. Start with the embedding model above, then swap in your own ONNX export from Lesson 09.
  2. Measure the first visit. Open the page in a fresh private window with the network panel recording. Write down three numbers: bytes over the network, then milliseconds to a ready pipeline and to the first output.
  3. Measure the second visit. Reload. Write down the same three numbers. The bytes should be zero. Explain, in one sentence, any part of the load time that did not collapse.
  4. Measure the no-GPU path. Force the WebAssembly backend, log crossOriginIsolated, and check whether you are on one thread or several.
  5. Build the download screen. Show the byte count before starting, show progress during, and handle the case where the cache was evicted between visits.
  6. iOS track. Put your .pte or .mlpackage into an Xcode project and build it twice: once with the model inside the bundle, once downloading it on first run. Record the app download size both ways.
  7. iOS track. Run it under Instruments. Record peak memory, and open the Core ML Instrument to see which compute unit each region of the graph actually used.

Then break it on purpose. Each of these is a bug report you will otherwise receive from a stranger:

  • Clear site storage between runs. Throttle the network panel to a mobile profile. How long is the first visit now?
  • Delete the downloaded model file while the app is closed, then launch. Does it recover, or show an error screen with no way forward?
  • Remove the COOP and COEP headers from your server and measure the WebAssembly path again. Nothing errors — how much slower did it get?
  • Generate continuously for five minutes on a phone. Plot tokens per second against time and find the moment the clocks drop.
  • Raise the maximum context length until the app is terminated. Compare that number with the one you predicted from the table in section 7.

Check yourself

Your iOS app takes 2.8 seconds from launch to the first token. You measure the three parts and find 12 ms to map the file, 2 400 ms to compile, and 380 ms to prefill. Which change helps most?

Compilation is 86% of the total, so nothing else can matter much. The .mlmodelc that Core ML builds on first load can be produced ahead of time and stored, which turns 2 400 ms into tens of milliseconds on every launch after the first.

Your Transformers.js page loads in under a second every time you open it. Users report a 40-second wait, then instant loads afterwards. What is happening, and what do you change?

Cache Storage is keyed by URL and filled once per origin, not once per visit, so after your first run your machine sits permanently in the good case. Nothing is broken: the users are seeing the first visit and you are not. Fix the measurement, then design the first visit as a real download screen. Storing compiled shaders is not offered to you in a browser, and dtype chooses how many bytes are downloaded, so fp32 would make the wait longer.

On a laptop with no WebGPU, your page runs at full speed from your development server and about six times slower from the production URL. Same browser, same machine, nothing in the console. What do you check first?

With no WebGPU you are on the WebAssembly path, and its speed comes from worker threads. Threads need SharedArrayBuffer, which needs a cross-origin-isolated page, which needs both headers. Your development server sets them and your host usually does not. Nothing errors, so log crossOriginIsolated in production. The slowdown tracks the threads you lost, roughly four to eight on current devices — measure it rather than trusting the number.

Your app maps 1.83 GB of weights from a file and also holds a 0.9 GB KV cache. The device comes under memory pressure. What does the operating system do?

Memory-mapped weights are clean, file-backed pages: an identical copy already exists on disk, so dropping them costs only a later re-read. The KV cache is dirty anonymous memory that exists nowhere else, so the only way to reclaim it is to terminate your process.

A foreground app may hold 2.5 GB. Your weights are 1.83 GB and the rest of the app is 0.25 GB. The KV cache costs 131 kB per token. What maximum context length do you ship?

2.5 − 1.83 − 0.25 = 0.42 GB for the cache, and 0.42 GB ÷ 131 kB is about 3 200 tokens. That is where the app dies on a quiet device, and what the model was trained for does not enter the sum. Ship well under it — 2 048 tokens is 0.27 GB — then confirm the prediction with the project's termination test.

Your closed iOS app needs a voice. Piper is GPL-3.0. Kokoro-82M is Apache-2.0 and 60–80 MB. Piper sounds slightly better in your listening test. What do you do?

Copyleft asks anyone who distributes the software to publish their own source under the same terms. A closed app cannot, and "it is only data" is not a defence you get to make on your company's behalf. The listening test is real, but it is not the deciding input — which is what makes this a licence decision, not a technical one.

Key words from this lesson
App bundle
The signed folder installed on a phone: your code, the runtime library, and any files you shipped with them.
Memory mapping also: mmap
Making a file's bytes appear in your address space, so nothing is copied and pages load only when touched.
Clean page / dirty page
A clean page has an identical copy on disk and can be dropped safely. A dirty page exists only in memory and can only be kept or lost with the process.
Cold start
The time from launching the app to the first useful output, when nothing is cached yet.
Delegate also: partition, island
A part of the model graph that one accelerator agreed to run. The rest stays on the CPU, and each boundary costs a tensor copy.
Neural Engine a kind of NPU
Apple's fixed-function accelerator for neural network operators. Very efficient, and restricted in the operations and layouts it accepts.
On-demand resources
Large files an app fetches from the store after installation instead of shipping in the download.
Cross-origin isolation
A browser state, switched on by two response headers, that a page needs before it may use shared memory between threads.
Thermal throttling
The device lowering its clock speeds because it is too hot. It is why a ten-second benchmark on a phone is not a result.
Jetsam iOS memory kill
The system terminating an app that exceeded its memory budget. There is no swap and no warning the user can act on.
