When it breaks

Three things will cost you days in this course: a model that will not learn, a machine that runs out of memory, and a session that dies after two hours of training. None of them are interesting problems. This page makes all three short.

fix · 1The model will not learn

The loss sits flat, or goes to nan, or falls but the output is nonsense. There is a correct order to check things, and most people do it backwards — they start tuning the learning rate, which is check number six.

Work down this list. Stop at the first check that fails.

  1. Overfit ten examples. Take ten samples, turn off shuffling and any augmentation, and train on only those. A correct training loop drives the loss to nearly zero in under a minute. If it cannot, the bug is in your code and no hyper-parameter will save you. This one check finds most bugs.
  2. Check the loss at step zero. Before any training, the loss should equal the loss of pure guessing: ln(number of classes). For 10 digits that is 2.30. For a language model with a 50,000-token vocabulary it is 10.82. If your first loss is far from that number, your labels, your shift or your loss function is wrong — not your model.
  3. Decode one batch back into what it really is. Print the images, or detokenize the input_ids and the labels side by side and read them. For a language model, confirm the labels really are the inputs shifted by one, and that padding is masked out with -100. Data bugs look exactly like model bugs from a distance.
  4. Check that gradients exist. After backward(), print the gradient norm. If it is None for a parameter, that parameter is not connected to the loss. If it is nan, something divided by zero or overflowed — often a log(0) or fp16 overflow inside attention.
  5. Check that the parameters actually change. Save a copy of one weight tensor, run one step, compare. If nothing moved, you probably forgot optimizer.step(), or the parameters were never handed to the optimizer, or they are frozen with requires_grad=False.
  6. Now, and only now, the learning rate. Try a few values a factor of ten apart and watch the first hundred steps. Loss exploding means it is too high; loss barely moving means too low.
  7. Bisect the data. If ten examples train and the full dataset does not, the problem is in the data you have not looked at. Halve it until the failure disappears.

import math, torch

# 2. is the starting loss what pure guessing looks like?
with torch.no_grad():
    logits = model(next(iter(loader))[0].to(device))
print("step-0 loss", criterion(logits, labels).item(),
      "expected", math.log(num_classes))

# 4. do gradients exist, and are they finite?
loss.backward()
total = 0.0
for name, p in model.named_parameters():
    if p.grad is None:
        print("NO GRADIENT:", name)          # not connected to the loss
    elif not torch.isfinite(p.grad).all():
        print("NAN/INF GRADIENT:", name)
    else:
        total += p.grad.norm().item() ** 2
print("grad norm", total ** 0.5)             # healthy is roughly 0.1 to 10
Remember this

If you learn one habit from this course, make it check number one. A model that cannot overfit ten examples has a bug, not a tuning problem. The test takes a minute and it is decisive.

fix · 2You ran out of memory

Training uses far more memory than inference, and the reason is not the weights. For every parameter you also store a gradient, and AdamW stores two more numbers on top of that. In Lesson 01 you saw the headline figure; here is where each byte goes.

What is storedBytes per parameterFor 1B parametersCan you avoid it?
Weights (fp32)44 GBUse bf16, or freeze them
Gradients44 GBOnly for trainable parameters
AdamW state (two moments)88 GBLoRA, or an 8-bit optimizer
Subtotal≈ 16≈ 16 GB
Activationsdepends on batch and sequence lengthoften 2–10 GBGradient checkpointing, smaller batch

Read the last row carefully, because it is the one people forget. LoRA removes the gradient and optimizer rows, but not the activation row. If you switched to LoRA and still ran out of memory, activations are what is left, and the fixes for those are different.

The activation problem, and gradient checkpointing

The backward pass needs the values computed on the way forward. So by default every layer keeps its output in memory until the backward pass reaches it. Activation memory grows with batch size, sequence length, model width and depth — all four at once.

Gradient checkpointing is the trade: throw most of them away, keep only a few, and recompute the missing ones during the backward pass. You pay roughly 30% more time and you get a large fraction of the memory back. On a laptop this is usually the difference between running and not running.

memory_fixes.pypython
# In the order you should try them.

# 1. Smaller micro-batch, same effective batch (Lesson 01: gradients accumulate)
accum = 4
for i, (x, y) in enumerate(loader):
    loss = criterion(model(x), y) / accum     # divide, because .grad sums
    loss.backward()
    if (i + 1) % accum == 0:
        optimizer.step()
        optimizer.zero_grad()

Reading the error

On CUDA the message tells you how much it wanted and how much was free — believe those numbers. On Apple Silicon the memory is shared with the whole system, so the limit moves depending on what else is open. If a run fails at the same step every time it is genuinely too big; if it fails at a random step, close your other applications and try again before changing any code.

fix · 3Your session died

Free Colab sessions are killed when idle and capped weekly. Laptops go to sleep. Any run longer than about twenty minutes needs to be resumable, and that is a property of what you save, not of how often you save it.

A checkpoint that only contains the weights is not resumable. Restarting from it resets the optimizer moments and the learning-rate schedule, which usually shows up as a visible jump in the loss curve at exactly the point where you restarted.

checkpoint.pypython
def save(path, step):
    torch.save({
        "step": step,
        "model": model.state_dict(),
        "optimizer": optimizer.state_dict(),     # the Adam moments
        "scheduler": scheduler.state_dict(),     # where the LR schedule was
        "rng": torch.get_rng_state(),            # so the data order continues
    }, path)

def load(path):
    ck = torch.load(path, map_location=device)
    model.load_state_dict(ck["model"])
    optimizer.load_state_dict(ck["optimizer"])
    scheduler.load_state_dict(ck["scheduler"])
    torch.set_rng_state(ck["rng"])
    return ck["step"]                            # carry on from here
  • Save every N minutes, not every N steps — you care about wall-clock lost, not steps lost.
  • Keep the last checkpoint and the best one. Overwrite everything else; they are large.
  • On Colab, save to Google Drive. The session disk disappears with the session.
  • Write one line per evaluation to a CSV: step, train loss, validation loss, learning rate, wall-clock. When you later ask "was run B actually better", this file is the only thing that can answer.
One change at a time

The temptation, when a run is disappointing, is to change the learning rate and the batch size and the model width together. Then the next run is better and you have learned nothing, because you cannot say which change did it. Give every run a name, change one thing, and write down what you expected to happen before you start it.
